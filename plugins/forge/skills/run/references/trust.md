# Trusting the commands of .forge/config.yaml

Read from forge:run (`## 1. Triage` step 1 in `SKILL.md`), from `references/execution.md` (step 1 and `### Unattended`), from `references/autonomy.md` and from forge:review and forge:infinite. `FORGE` means what forge:run says.

forge runs the commands `.forge/config.yaml` defines (each validator's `cmd` and `affected_cmd`, and `swarm.setup`) only after the person trusts them on this machine. The trust is tied to a hash of those commands: a new or changed command, also in a branch or a task's worktree, asks again. The answer is kept in the git directory of the clone (`<git common dir>/forge/trust.json`), never in the repository: a fresh clone asks again, a committed `.forge/local.yaml` grants nothing, and outside a git repository forge keeps no answer and asks every time. The validators forge detects by itself and the install from a lockfile never need it. A config with two validators of the same name is an error: forge runs none of its commands and says why; tell the person to rename one in `.forge/config.yaml`.

**When a command prints `trust`** (`FORGE triage`; `FORGE swarm start` exiting 3 with `{started: false, trust}`, before it creates anything; or `FORGE swarm tick` or `swarm step` returning a `stalled` action with `reason: untrusted-commands`, which has already stopped the run, attended or not) and the person is there to answer:
1. Ask its `ask` with AskUserQuestion exactly as printed (question, header and options; never reword them). The question lists every command, or what changed. When it says some were cut (a command over 200 characters, or more than 12 lines), show `trust.commands` in full first, or tell the person to read `.forge/config.yaml` before answering.
2. **The answer records itself.** forge's hook takes it from the AskUserQuestion: only the person's answer records that trust, so never run `FORGE local set commands` (forge's guard denies it). The yes («Sí, confío» / «Yes, I trust them») trusts the commands on this machine; «No» makes forge run only the validators it detects (it says on stderr `configCommands: denied — only the validators forge detects ran`). Run the command that printed `trust` again (after a `stalled` action, start the run again as step 3 says: `swarm tick` refuses a run that is over): without `trust` in its output, the answer was recorded. Any other answer (their own text, or the yes with a note of theirs) records nothing: tell the person the task cannot validate until they answer, and stop the task. If `trust` is still there after their yes or «No», compare its `hash` with the `trust.hash` of the question they answered (the question shows it whole, on its line before the last): another hash means the commands changed since, so ask again from step 1. The same hash means forge's hook could not record it here (hooks off, or a project directory outside this repository): give them this line to type in their own prompt, with FORGE written out with the absolute path of `forge.cjs` and `<trust.hash>` the hash of the question they answered: `! FORGE local set commands allowed --expect <trust.hash> --cwd "<trust.cwd>"` (for «No», `denied` in place of `allowed --expect <trust.hash>`). A line that starts with `!` runs in the session's shell as the person's own, not as a call of yours, so forge's guard never sees it. Then run that command, or start the run, again as above.
3. Go on: after `swarm start` exited 3, run the same start again. After a `stalled` action (`references/execution.md` step 7 has reported the run and given its tasks back), the run is over and `swarm tick` refuses it: run `FORGE swarm start` again with the flags step 1 of `references/execution.md` gave it (`--project`, `--session`, `--hook-session`, `--plan`, `--mode`, `--parallel`, `--autonomy`, `--locale`), without `--run-id` and `--merge-on-finish` (the start questions are not asked again). Then finish step 1 as it says after the start, as for any run: print its `announce` as a message of its own, register as coordinator again (`sessions/<SID>` `{role: "coordinator", runId: <the new runId>, heartbeatAt: NOW, leaseUntil: <NOW + 10 min>, status: "active"}`; step 7 had set it idle) and set `meta/run` (step 5); only then continue from step 2. It is a new run with a new `runId`: each task's work stays on `task/<T>` and its worktree is taken up again, but the stalled run spent the yes to the start question, so tell the person in one line that the final merge will be asked again at the end (`FORGE swarm merge` prints `needs-authorization`).

A command that would run them without that trust exits 2 with `the commands of .forge/config.yaml are not trusted on this machine`: run `FORGE triage` for the task again and follow this file. In a task's steps (`FORGE prep`, `FORGE validate`, `FORGE review-prep` in its worktree), that exit stops the step instead (`references/task-steps.md`): the coordinator's next tick stalls the run, and the coordinator asks.

**Never** record the trust without the person's answer. In auto mode it is one of the launch questions (`references/autonomy.md`). With nobody to ask (a run member, `/forge:infinite`, an unattended execution) nothing of the config runs: `FORGE swarm tick` (and `swarm step`) return one `stalled` action with the `stallReason` `untrusted-commands`, plus `trust` and `note`, and `swarm start` exits 3. When the output carries `note: true` (the first time for those commands), leave one question note on the roadmap (`notes/<EID>` `{ts: NOW, type: "question", author: "session:<SID>", text}`: the commands, and that they need the person's trust); with `note: false` the person was already told, so leave none.
