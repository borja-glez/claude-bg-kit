# A task's steps

Shared by forge:run (the coordinator, Execution step 4, for tasks of mode `subagents`) and forge:member (a run member, in its own session). `FORGE`, `WP`, `DB`, `SID`, `<plan>` and `<project>` mean what the skill that sent you here says. Where a step cites a section of forge:run, read it when you reach it: Medium step 3b and Medium step 6 in `../SKILL.md`; Execution step 4 `integrate`, step 5 and `### Unattended` in `references/execution.md` (next to this file).

**A task's steps** (the coordinator runs them for tasks of mode `subagents`; a run member runs the same steps in its own session, forge:member. State in the execution: `FORGE swarm status` shows each task's stage, agent, round and worktree; record it with `FORGE swarm task <T> --stage <S> --agent <A>|--no-agent --round <n>` at every change, which also writes `.forge/execution/<T>.json`). Publish each stage change, and each verdict, with one ArtifactData `batch`, never with separate calls: `update state/T` with both `state/T.exec` (the same `{stage, agent, round, since}` plus `leaseUntil`) and `state/T.forge` (`forge: {path, phase, agent, validators: [{name, ok}], verdict: {action, score}, round, cap}`, small, no findings text; `path` is the path of the task's latest triage: step 3's once it ran) pinned to `TV` (the task's version), and the lease of `sessions/<SID>` (`update` `{heartbeatAt: NOW, leaseUntil}`) pinned to its version, never shorter than the one it already holds while another task's agent is still running (Execution step 5: never shorten a lease set for an agent that is still running); when step 5 publishes `meta/run` at that moment, its `slots` go in the same batch. `leaseUntil` is `NOW + 10 min`, except when the change dispatches an implementer, reviewer or verify agent: you will not step while it runs, so pass `--lease <NOW + the agent's expected budget, at most 90 min>` to that `FORGE swarm task` call and put the same `leaseUntil` in both; when it returns, the 10-min renewal of step 5 resumes. On `version_mismatch` follow waypoint's lost-task rule. `<n>` is the brief number (1 unless a `redo` starts a new brief). Before the first task, list `proposals` into `DB` and run `FORGE proposals pull --dir DB/proposals`.
1. **brief**: `mkdir -p .forge/work/T && FORGE brief --plan <plan> --task T > .forge/work/T/brief-1.md`, add what the task needs from the design and from earlier tasks, and the absolute worktree path with "work only inside this directory". `FORGE triage --plan <plan> --task T --cwd <worktree>` (in the worktree, so it sees the validators the run branch already has); its `implementer` is who implements the task in step 2. Then `FORGE prep --task T-1 --path large --cwd <worktree>`: in one call it reads BASE (the worktree's HEAD, the `base` it prints), records what already fails on it into `.forge/work/T/baseline-1.json` and logs the phase `implement` with the brief and that base; never record them separately. The one exception is a conflict retry (Execution step 4 `integrate`, and its ephemeral twin): it re-runs the baseline on purpose with `FORGE validate --all`, as that step says, because the brief's BASE moved to the tip it merged, and keeps the phase `implement` that `prep` logged.
2. **implement**: spawn the implementer, the triage's `implementer.agent` as printed (a plan task is never implemented by the coordinator: a Trivial one goes to `mech`, a Large one to `impl` (`impl-high` on a sensitive zone)), or `impl-high` when the design marks the task delicate; in fix rounds, the implementer `FORGE review-close` prints (`implementer.agent`; `resume` keeps the same one) and never compute the ladder by hand; log every implementer you spawn, first attempt and fix rounds, with `FORGE log --kind agent --task <T>-<n> --data-file <f>` (`{"agent":"<name>","role":"<role>"}`) (a delicate task logs `impl-high`), since `FORGE review-close` reads the previous rung from it, **in the background**, with the brief, the worktree, the report path and the absolute FORGE path. Ask it to commit in the worktree on `task/<T>` with the brief's `Commit title prefix` and to reply in two lines; everything else goes to its report file.
3. **validate** (when it returns; `<base>` is the `base` that `swarm worktree` printed, or the one moved after a conflict retry, step 4 `integrate`): a plan task is first sized again (still stage `validate`) with `FORGE triage --plan <plan> --task T --cwd <worktree> --base <base>` (add `--delicate` when the design marks the task delicate, so the reviewers' efforts follow): it sizes the task again from its real diff (the real diff alone sizes it, the plan-time estimate sets no floor; a sensitive zone, from its text, its plan zones or its diff, keeps it at Medium at least; and across the task's fix rounds the size only goes up) and its `review` says who reviews it (`review.reviewers`, with the verdict flags in `review.flags`). Then, instead of validating and writing the diff yourself, `FORGE review-prep --task T-<n> --path large --base <base> --baseline .forge/work/T/baseline-1.json --dir .forge/work/T --cwd <worktree>` (the same `<base>`): it validates against the baseline into `.forge/work/T/validators-<n>.json`, writes `.forge/work/T/diff-<n>.patch` (from round 2 also the fix diff and each reviewer's own previous findings), reads that triage's `review` and prints `round`, `validators` and `spawn` (who reviews, how and with what), plus `carried`: the reviewers whose previous result is copied to the new round, not spawned again.
4. **verify** and **review**: `FORGE verify-plan` as Medium step 3b with `--path` the path the triage of step 3 printed (and `--cwd <worktree>`; on Trivial and Small it verifies only when the task asks for it). Then spawn exactly the entries of review-prep's `spawn`, each as its `agent` with its `mode` (`full` or `delta`) and its `inputs` (the brief, the diff, the validators file and `out`, the review dir `.forge/work/T/reviews-<n>-<round>/`; with `mode: delta` also `fix`, the fix diff, and `findings`, its own previous findings; `report`, for `review-correctness`, the implementer's report path when the brief has a `TDD: required` line), passing the Agent tool's `model` when it is not null and the Agent tool's `effort` always (a light review is one `review-correctness` on Sonnet at medium effort, so this session never reads the diff itself). A `twin: true` entry is spawned the same way: its `out` is the round's `shadow/` folder and it never counts in the verdict. Spawn `verify` too when chosen, with that review dir; all of them **in the background, in parallel**. Each replies in two lines. A path that grows to Large here is reviewed with the reviewers it prints, and is not blocked, also when the execution is unattended (the Large row of `### Unattended` in `references/execution.md` is about a request triaged Large before any work).
5. **verdict**: when the last of them returns (each one that returns without its file is respawned at once; never end the turn with one missing and no agent running), `FORGE review-close --task T-<n> --dir .forge/work/T --path large --cwd <worktree>`: it runs the verdict with the triage's flags and the round decision in one call (no separate verdict or round). Run it only once every spawned entry has returned, twins included: review-close compares only the twins whose file is there when it runs, so a twin that finishes later is lost. Exit 3 with `missing`: respawn each reviewer whose file it lists, with its same `spawn` entry, and close again when it returns. `invalid` or `incomplete` as Medium step 6. Then follow `next`: `done` → `FORGE swarm task <T> --stage verdict --status accepted --no-agent`; when it printed `deferred` findings (review-close already logged them as a ruling), write that array with the Write tool to `<MAIN>/.forge/work/<T>/deferred.json` (`<MAIN>` the main checkout: the coordinator's own `.forge/work/<T>/`; a run member writes it there as it writes `handover.md`), for the closing report to list them, one line per finding with its file and line, for the person to decide. `resume`, `fresh-stronger` or `redo` → back to implement with `findings` (the file review-close wrote: the findings to send) and its `implementer` (Medium step 6 rules, cap 4); steps 3 and 4 then run again, sizing included, and the reviewers follow the new size and review-prep's new round. `breaker` or `stalled` with blocking findings → `FORGE swarm task <T> --status blocked --detail-file <f>` and the waypoint blocked path for `state/T`.
