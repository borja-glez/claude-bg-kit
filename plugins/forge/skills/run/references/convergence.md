# Convergence of the review loop

Read from forge:run (Medium steps 3, 5 and 6 in `SKILL.md`) and from `references/task-steps.md` (steps 2, 4 and 5). `FORGE` and `<id>-<n>` mean what the skill that sent you here says; in an execution every FORGE call also takes `--cwd <worktree>`, as the task steps do.

**Reviews and residuals.** review-prep and review-close print `reviews`: review `n` of at most `max` (4 reviews on Medium, 5 on Large). Every critical and important finding has an `id` (`F1`, `F2`…) for the whole brief, kept in `findings-index-<n>.json`. review-close's `deferred` lists the findings that do not block, each with its `id` and its `residual` (`untouched`, `docs`, `late-round`, `hardening`, `cap`, `out-of-model`, `architecture`): the task goes on, and the report that closes the work lists each one with its id, its `residual`, file and line, for the person to decide. When a round opens anyway, the `untouched`, `docs` and `late-round` ones also go to the implementer.

**Express review.** With `express: true`, review-prep did not validate: its `validators` is `{pending: true, cmd, file}`. Run `validators.cmd` exactly as printed with `run_in_background: true` and, at the same time, spawn its single `spawn` entry (`review-correctness` on Sonnet at medium, `mode: delta`; tell it `express: true` and give it its `inputs`). Wait for both: review-close exits 3 with `missing` naming `validators-<n>.json` until that file is there. review-close exits 2 and removes that file when the background validation gave no results (a bad `--baseline`, an invalid config); its message says why. Then, or when the background command ended and the file is still missing, run `validators.cmd` once more in the foreground; if it fails again, tell the person and stop. Red validators in it make the verdict a fix like any other.

**Twins.** Close the review once every spawned entry that is not a twin has returned; never wait for a twin. review-close saves the twins already back and lists the others in `shadowPending`; when one of those returns, run `FORGE shadow collect --task <id>-<n> --dir <its review dir, reviews-<n>-<round>>` (it never changes the verdict).

**A repeated security theme (`ask`).** With `ask` in review-close's output (security found another variant of a finding already closed), ask the person its `question` with its `options` in one AskUserQuestion before you follow `next`:
- `fix`: follow `next` as printed.
- `out-of-model`: run the same `FORGE review-close` again with `--out-of-model <the ids of ask.findings, comma-separated>`; it closes the same review again with them as minor findings out of the threat model, and you follow its `next`. Then offer once to add the theme to `threatModel.outOfScope` in `.forge/config.yaml`, and edit that file only after the person's yes (it is theirs). Without a `threatModel` there, the new section also needs `protects` (at least one entry): ask for it in the same question, or offer the default's wording «the person's files and git history outside the task's worktree». After the edit run `FORGE config get threatModel`: if it exits 2, undo your edit and tell the person.
- Nobody to ask (autonomy `auto`, or an unattended execution): take `out-of-model`, record the decision with `FORGE decision add` (`"point": "ruling"`, `"undo": {"type": "none", "reason": "..."}`, as `references/decisions.md` says) and leave a question note for the person.
- In an execution stepped with `FORGE swarm step` (`references/step.md`), the step closes the review and follows `next`: give it the answer with `--ruling <T>:fix`, `<T>:out-of-model` or `<T>:defer:F3[+F5]` on the next step, and never run `review-close` or follow `next` yourself. The `threatModel` offer above is still yours.

**An architectural change in a fix round.** A fix-round implementer that stops with NEEDS_CONTEXT proposing an architectural change (where state lives, a storage format or location, a module boundary, a public interface the brief does not ask for): ask the person, «apply it» or «keep the architecture and leave the finding open». Never decide it yourself. «Apply it»: resume the implementer with the answer. «Keep»: run the same `FORGE review-close` again with `--defer <the finding's id>` (it becomes residual `architecture`) and follow its `next`; under `FORGE swarm step`, step again with `--ruling <T>:defer:<the finding's id>` instead (never run `review-close` yourself while stepping). Nobody to ask: keep the architecture, `--defer` (or that ruling), record the decision (`"point": "ruling"`, `"undo": {"type": "none", "reason": "..."}`) and leave a question note.

**A new implementer.** With `next` `fresh-stronger` or `redo`, review-close wrote `handover` (`handover-<n>-<round>.md`): give its path to the new implementer with the brief. A `redo` first undoes the attempt: run git with `revert.args` as printed; if that revert stops on a conflict, run `git -C <repo> revert --abort`, tell the person and stop. With `revert.steps` instead of `args` (the attempt's range holds a merge: a conflict retry merged the run branch into the task), run git with each of its argument lists, in order, as printed: they restore BASE's tree in one commit, so the run branch's work BASE holds stays. Never `git revert -m 1` over such a range: it would also undo the run branch's work. If a step fails, tell the person and stop.
