# Resuming

Read from forge:run (`## Resuming` in `SKILL.md`). `FORGE` and `<id>` mean what that skill says.

1. `FORGE last --task <id>`: `path` and `phase` (the whole last phase event, with its `brief` number `n`).
2. `FORGE last --task <id>-<n>`: the last verdict (with its review `dir`) and the last round of that brief.
3. Continue from there; the phase event's `base` is the `BASE` for `redo` (in an execution, after a conflict retry, `.forge/work/<T>/base-<n>.json` holds the base the reviews moved to: when it exists, its `base` is the `<base>` of the task's next steps); never redo finished work. If the last verdict already covers the newest review dir, do not close that round again: follow the `next` of the last round. Run `FORGE review-close` only for a round review-prep prepared that has no verdict yet (on Large's final review, `FORGE verdict` only for a final dir that has none).
4. In an execution (`FORGE swarm status` shows it active and you are its coordinator; the SessionStart context says "Resume it with /forge:run → Resume", or you came back with `claude --resume`): renew your lease, then run `FORGE swarm start` with the same `--project` and `--session`, `--hook-session <CSID>`, plus the `--mode` and `--parallel` that `FORGE swarm status` shows (and `--kind ephemeral` for an ephemeral run, which then follows `references/ephemeral.md` → Resume) (it resumes without changing anything but the binding: this Claude session becomes the one the Stop hook steps, also after a `/clear`; without them `start` takes the mode and N from `.forge/config.yaml`). Reconcile each task in `running`: a subagents task as before, reading its stage, agent, round and worktree from `FORGE swarm status` and its review dirs (`.forge/work/<T>/reviews-*`): an agent that is not running any more is respawned for that step; a verdict already written is not recomputed. A sessions task by ListAgents: a live `wp-<project>-<T>` session is left alone; a dead one gets the `relaunch` action of the next `tick`. Then go to `references/execution.md` step 2. An execution started in auto (`FORGE swarm status` shows `autonomy: auto`) keeps deciding alone as `references/autonomy.md` says.
   **Takeover.** A `FORGE swarm start` that exits 2 naming `swarm takeover` (another session coordinates the run) comes here too. A new session asked to go on with the execution ("sigue con la ejecución") while another session coordinates it: get `SID` (`/waypoint:work` §0 Setup items 1–4), list `sessions` into `DB` (`references/execution.md` step 2), then `FORGE swarm takeover --session <SID> --hook-session <CSID> --db DB`. `took: true` → register as coordinator (`sessions/<SID>` as `references/execution.md` step 1, with its lease; `--hook-session` already bound this session, so its Stop hook steps you), claim again with a versioned write the `owner` of each task it lists as `running` whose `executor` (`FORGE swarm status`) is `subagents` (`update state/T` `{owner: SID, exec: {by: SID}}` pinned to its version), publish `meta/run` (`references/execution.md` step 5) and go on from step 4 above. `took: "already"` → you already coordinate it: step 4 above. `took: false` → tell the user who coordinates it (`previous`, and its `liveness`) and join as a manual member (`/waypoint:work`, which sends you to `references/manual-member.md`).
