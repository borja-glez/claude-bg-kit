# Stepping with swarm step

Read from `references/execution.md` step 3. `FORGE`, `WP`, `DB`, `SID`, `<plan>` and `<project>` mean what that file says. One `FORGE swarm step` does, in one command, the tick, the task steps of every task that came back (`references/task-steps.md`) and at most one integration; you run it in the background, act on what it prints and publish it in one batch.

1. **Run it.** Write `.forge/work/run/versions.json` with the Write tool from the versions the `list` of Execution step 2 printed: `{"state": {"<T>": <version>}, "sessions": {"<SID>": <version>}}`. Then run `FORGE swarm step --plan <plan> --db DB --versions .forge/work/run/versions.json --locale <es|en> --out .forge/work/run/step.json` with the Bash tool's `run_in_background: true`, after `rm -f .forge/work/run/step.json` in the same Bash call, so a step that dies leaves no old file (in mode `sessions` add `--agents .forge/work/run/agents.json` when Execution step 2 wrote it; add `--returned <T1,T2>` with the tasks whose agent came back since the last step, and `--ruling <T>:<answer>` for each answer the person gave since then, step 4). A task in review goes in `--returned` only once every reviewer it was waiting for is back, a respawned one included, and in an express review once its background validation ended: `--returned` forces review-close, and naming it early gives `reviewMissing` and duplicate reviewers. Never give it a `timeout`: in the background there is no 10-minute limit. Then end the turn as step 5 says (with the step running, only the `--mark`): its end wakes you, as an agent's return or the sleep does. One step at a time: when you wake while a step still runs (an agent came back), keep that task for the next `--returned` and end the turn.
2. **Read** `.forge/work/run/step.json` with the Read tool. With `busy` (another step still runs: `.forge/jobs/step.lock`), end the turn as step 5 says, with only the `--mark`: the running step's end wakes you; keep its `--returned` and `--ruling` for the next step. With `error` and `code` at the top (the command failed): this once, do Execution steps 3 and 4 with the single commands, and step again next time. With no `step.json` (the step died before writing it), or with a task at `implement` or `review` whose agent is not running and was never handed out, step again with `--returned <that task>`. A `readReport` for a report that does not exist means its implementer never ran: spawn it again as `references/task-steps.md` step 2 says.
3. **Publish** its `publish` in one ArtifactData `batch`: for each entry of `publish.tasks`, `update state/T` with its `exec` and its `forge` pinned to its `version` (with `claim: true`, also `status: "in_progress", owner: SID, claimedAt: NOW, startedAt: NOW`, and a `started` event); `update sessions/<SID>` `{heartbeatAt: NOW, leaseUntil: <publish.session.leaseUntil>}` pinned to its `version`; and `update meta/run` with `publish.metaRun` (`set` it the first time). A `version_mismatch` on a `claim: true` task means someone claimed it: `FORGE swarm task <T> --drop` and do not spawn its implementer. Print its `say` as it is.
4. **Act** on each of its `actions` (by its `type`), in order. Every agent goes **in the background**; give each the absolute FORGE path. The step already recorded each stage and logged each implementer it hands out: do neither again. Print an action's own `say` (review-prep's line) as it is.
   - `spawnImplementer` (`task`, `agent`, `brief`, `report`, `validate`, `worktree`): spawn `agent` with the brief, the worktree, the report path and the `validate` command (`references/task-steps.md` step 2; the step already logged the agent). Add to the brief what the task needs from the design or from earlier tasks only when it helps. A `setup` with `ok: false` is told in one line, as Execution step 1 says.
   - `spawnReviewers` (`task`, `round`, `spawn`, `carried`, `path`, `base`): `FORGE verify-plan` and its surfaces as `references/task-steps.md` step 4 says (`--path` the `path` printed, `--base` the `base`, `--dir` the round's review dir: the step then waits for `verify` too), then spawn exactly the entries of `spawn` as that step says.
   - `express` (`task`, `validate`, `spawn`): run `validate` with `run_in_background: true` and spawn its single `spawn` entry (`references/convergence.md`).
   - `validatorsRound` (`task`, `implementer`, `findings`): resume that implementer with the `findings` file (only those failing validators).
   - `readReport` (`task`, `report`): read the report; NEEDS_CONTEXT or BLOCKED as `references/task-steps.md` step 2 and `references/convergence.md` say. A question for the person (an architectural change): ask the person (`references/convergence.md`), then step again with `--ruling <T>:<answer>` («keep the architecture» is `defer:<id>`); «apply it» resumes the implementer with the answer. A report that says the finding is already fixed, or is wrong, with no commit: step again with `--ruling <T>:review`, which prepares the next review on the same HEAD. Never run `review-close` yourself while stepping.
   - `respawnReviewers` (`task`, `spawn`) and `reviewMissing` (`task`, `missing`): spawn again, once, each entry or the reviewer of each missing file, with its same `spawn` entry and dir (a `verify` entry, or a missing `verify.json`: the verify agent, as `references/verify.md` says, with the `surfaces`, `brief`, `diff`, `dir` and `evidence` of its entry or of the round's `verify-pending.json`). A missing `validators-<n>.json` is no reviewer: it is an express review's validation, so run that round's `validatorsCmd` (in its `review-plan.json`, `.forge/work/<T>/reviews-<n>-<round>/`) once more, in the foreground, as `references/convergence.md` says.
   - `accepted` (`task`, `deferred`): nothing to spawn: the next step integrates it. `deferred` is the file the closing report reads.
   - `resumeImplementer`, `freshImplementer` (with `handover`) and `redo` (first run git with `revert.args` as printed, or with each list of `revert.steps` in order: `references/convergence.md`): send `findings` to `implementer.agent` as `references/task-steps.md` step 5 says.
   - `ask` (`task`, `close`): ask the person (`references/convergence.md`, a repeated security theme, with `close` as review-close's output), then step again with `--ruling <T>:<answer>`: `fix`, `out-of-model` or `defer:F3[+F5]`; the step follows it (until then it closes nothing for that task). Never run `review-close` yourself while stepping. Nobody to ask: `out-of-model`, as that file says.
   - Any action with `verify` (verify-close's output: the step closed the round's verification and committed the learned notes it lists in `commit` in the task's worktree): print its `say`, show its `proposals` as `references/verify.md` `## After the verdict` says, and do that section from the upload onward.
   - `blocked` (`task`, `reasons`): the waypoint blocked path for `state/T` (`references/task-steps.md` step 5).
   - `integrated`, `conflict`, `run-dirty`, `run-deps` (the fields `swarm integrate` prints, `commit` and `recovered` included): what Execution step 4 `integrate {task}` says after its command (the `done` batch with `summary` and `commits`, the call of its own to `meta/project`, the `say` lines, `swarm retry`…). After a conflict's `swarm retry`, the moved `<base>` and its baseline are the step's: it diffs the task from where its implementer merged the run branch. An `integrated` with `again: true` is a task integrated earlier whose `state/T` is still not `done` (that step's output or its batch was lost): do the same.
   - `start` in mode `sessions`, `relaunch`, `nudge`, `block`, `finish` and `stalled`: as Execution steps 4 and 7 say.
   - `error` (`task`, `command`, `stderr`): the next step retries it. Tell the person in one line the first time; tell them again only when the same error repeats on the next steps, and then stop that task (`FORGE swarm task <T> --status blocked --detail-file <f>` and the `blocked` path above) and say what failed. Never run a task's single commands while you are stepping: they are only the fallback of step 2, when the step command itself failed. The one exception is an `error` of `review-close` saying an express review's validation gave no results: run that round's `validatorsCmd` (its `review-plan.json`) once more, in the foreground, as `references/convergence.md` says. An `error` without `task` (the tick failed): tell the person, step again, and when the same error repeats, stop the run (`FORGE swarm stop`, then Execution step 7).
5. **Wait.** A `wait` of 0 right after an `integrated` action: step again at once (back to Execution step 2, a fresh `list`, so the next batch is pinned to fresh versions). Any other `wait` of 0, or none, is 300 (`swarm sleep 0` exits 2). Before ending any turn, always run `FORGE swarm sleep 300 --mark`; then, unless a background command of yours is running (a step, an integrate, a validation, or a sleep already started), also run `FORGE swarm sleep <wait, at most 300>` with `run_in_background: true`, and end the turn without other text (Execution step 6).
