# Ephemeral execution

Read from forge:run (`### Ephemeral execution` in `SKILL.md`). `FORGE` and the Medium steps cited here mean what that skill says. `<WORK>` is a loose task's work folder, `.forge/work/<T>` (the `work` that `FORGE swarm worktree` prints).

Parallelism outside a plan (spec §4.4): the same scheduler and the `subagents` executor, with no waypoint plan, integrated **into the current branch** one task at a time.

**When.** A message with several requests ("haz A, B y C"): split them, write each one's text to `.forge/work/<id>/task.txt` and run `FORGE triage --task <id> --text-file .forge/work/<id>/task.txt --batch` for each. A Large one leaves the batch and follows `references/large.md` after it. Also a Medium task whose briefs can run in parallel (`## Medium` step 2 in `SKILL.md`). If only one task is left after the split and the triage, there is no ephemeral execution: it is a normal task.

**Medium briefs.** One loose task per brief: id `<id>-<n>`, path `medium`, zones the brief's files, `depends_on` the briefs it needs; a brief that depends on another starts once that one is integrated. Each brief's work files are then in `.forge/work/<id>-<n>/` (its loose task's directory: `brief-1.md`, baseline, validators, reviews). When the execution ends, the Medium task goes on with its step 7 in `SKILL.md`.

**Loose ids.** Loose ids repeat between runs, and a repeated id would inherit the ledger history (triage ratchet, round history) and the stale `<WORK>/` of an unrelated earlier task. So each loose id is `<slug>-<tag>`: `<slug>` a short kebab-case slug (at most 40 characters) and `<tag>` 4 lowercase base-36 characters derived from the time the run starts, the same for every task of the run: `node -e "console.log((Math.floor(Date.now()/1000)%1679616).toString(36).padStart(4,'0'))"`, run once, before the first `.forge/work/<id>/task.txt`. The result is at most 45 characters, so it passes the plan-id rule (`[A-Za-z0-9_.-]`, 64 at most) with room for a Medium brief's `-<n>`. Medium brief ids stay `<id>-<n>`, with `<id>` the Medium task's own id.

1. **Tasks.** With the Write tool, `.forge/work/loose-tasks.json`: `[{id, title, path, zones, depends_on}]`, one per request (or brief); `path` is `trivial`, `small` or `medium`. `zones` are the triage `files` (an empty list means the whole repository, so that task runs alone); `depends_on` lists the requests that need another one first (you judge it from the text: "luego usa eso en B").
2. **Start.** Check the tree as `Rules for every path` in `SKILL.md` says (changes that are not yours → ask first; when you ask, say that "leave them" means no task can be integrated — `integrate` answers `run-dirty` — until they are committed or stashed). When the project has a roadmap (`.waypoint/<project>/session.json` exists), bind first, as `references/execution.md` step 1 does: `node "<WP>" bind <plan> --via forge-run --claude <CSID>` (`<WP>` = `FORGE waypoint-cli`, `<plan>` = `docs/waypoint/<project>/plan.yaml`; exits 3 and 4 as step 1 says), so the roadmap seat whose SID coordinates is this conversation's; `SID` = its `sid`. Without one, `SID` = `loose-<UTC yyyymmddHHMMss>` (also when `start` refuses the waypoint id for its characters). `FORGE swarm start --project loose --session <SID> --hook-session <CSID> --kind ephemeral --tasks .forge/work/loose-tasks.json --locale <es|en>` (code 2 — another execution is active, a leftover worktree or branch of the same id, the checkout not on a branch —: tell the user its message and do the requests one after the other). It takes `parallel` = min(the configured N, how many tasks can run at once) by itself; do not pass `--parallel` unless the user gave one. Mode is always `subagents`; if the user asked for sessions, say in one line that an ephemeral run uses subagents. Print its `announce` as it is (the tasks, how many at once, that each lands on `<current branch>` as soon as it is accepted, and that `/forge:stop` ends it), plus one line when they show on the roadmap as loose tasks (only when the project has one). Then publish as `references/execution.md` step 5 says for an **Ephemeral run.**
3. **Loop.** `references/execution.md` steps 3, 4, 5 and 6, with these differences: `FORGE swarm tick` takes no `--plan` nor `--db`; there is no step 2; step 4 skips its DB, proposals and `state/T` parts (no listing into `DB`, no `proposals pull`, no `state/T` claim, mirror or `forge` update); step 5 is its **Ephemeral run.** paragraph (with a roadmap: `meta/run` with `kind: "ephemeral"` and `loose`, and your `sessions/<SID>` lease; never `state/T` nor the inbox; without one, nothing is published and lens and the band show the run from the local files). `start {task}`: `FORGE swarm worktree <T>` → `{worktree, branch, base, work, setup, resumed, prior}` (a task worktree off `<current branch>`), with no roadmap claim, then the task's steps. **A task's steps**, per task `T` with its own triage (a Medium brief: the Medium task's):
   - **brief:** write `<WORK>/brief-1.md` yourself from its request (or the Medium brief), with the absolute worktree path and "work only inside this directory"; with a non-empty `prior` from `FORGE swarm worktree`, write it to `<WORK>/prior.json` and append the output of `FORGE brief --task T --prior-file <WORK>/prior.json` (plus `--prior-total <n>` when it also printed `priorTotal` `<n>`) to the brief; then `FORGE prep --task T-1 --path <path> --cwd <worktree>`, with `--base <base>` too when `resumed: true` (BASE, the baseline `<WORK>/baseline-1.json` and the phase in one call; its `validate` goes to the implementer).
   - **implement:** spawn the agent named by the triage's `implementer.agent` for `T`, as printed, in the background (for a Trivial of a batch it is the `mech` role's agent, from `--batch`), as step 2 of `references/task-steps.md` says.
   - **validate:** Trivial and Small: `FORGE validate --all --path <path> --base <base> --baseline <WORK>/baseline-1.json --task T-1 --cwd <worktree> > <WORK>/validators-1.json`. Medium: `FORGE review-prep` as its step 3 with `--path medium`, without the plan re-sizing; a Medium brief's loose task `<id>-<n>` has no triage of its own, and review-prep then reads the Medium task's triage (`<id>`).
   - **Trivial and Small:** no reviewers. Read `git -C <worktree> diff <base>..HEAD` yourself: right → `FORGE swarm task <T> --stage verdict --status accepted --no-agent`; wrong → resume the implementer with what you found and validate again (after two such rounds, a fresh `impl`, the task having no `FORGE review-close` to print one; after that, `FORGE swarm task <T> --status blocked --detail-file <f>`).
   - **Medium:** verify, review and verdict as its steps 4 and 5, with `--path medium` on review-prep and review-close. Reviewers: exactly review-prep's `spawn` (`review-correctness` always; `review-security` only when the triage found a sensitive zone; `review-perf` only for performance tasks); review-close takes the verdict flags from the triage.
   - **integrate:** `FORGE swarm integrate <T>` merges `task/<T>` into `<current branch>` in the main checkout. `integrated` → no roadmap write; print its `say` lines as they are (new validators, and validators excused as already failing on `<current branch>`). `conflict` → tell the user in one line (with its `leftovers`, when there are any, and its `say` lines: an install in your checkout that was rolled back says so) and `FORGE swarm retry <T>` once. `run-deps` → as in a plan execution. Then read `<BASE>` with `git rev-parse <current branch>` and write it out literally (a shell variable does not survive between Bash calls): `git -C <worktree> checkout --detach <BASE>`, `FORGE validate --all --path <path> --base-run --task T-1 --cwd <worktree> > <WORK>/baseline-1.json`, `git -C <worktree> checkout task/<T>`; `<base>` = `<BASE>`. The implementer merges `<BASE>` (the sha, not the branch name) into `task/<T>`, so `<base>..HEAD` holds only this task's work: name that sha in its brief, with the conflict detail. If something was integrated meanwhile, the next `integrate` may conflict again; that is the second-conflict path: tell the user and leave it in conflict. `run-dirty` → your checkout has uncommitted changes: tell the user once that no task can be integrated until they are committed or stashed, and keep stepping. Code 2 because the main checkout is on another branch: tell the user to switch back to `<current branch>`, and keep stepping.
4. **End.** On `finish`: no final review and no `swarm merge`; the tick that finished the run also closed it (`closedAt`, `closedBy: merge`): there is nothing to close. Report one line per task (what changed, its implementer, its verdict or "read the diff"), one line per `deferred` finding with its file and line (from each task's `<WORK>/deferred.json`) and the checkable line «Ejecución <runId> terminada: N/N tareas integradas en <current branch>». Then the automatic decisions of the run (`references/decisions.md`, `--run <runId>`). On `stalled`: its reason per task. In both, with a roadmap: publish `meta/run` once more with `active: false` and `sessions/<SID>` `{status: "idle"}` (`references/execution.md` step 5, **Ephemeral run.**). **Cleanup.** On `finish`, offer to tidy up as `references/execution.md` **Cleanup** says: `FORGE swarm cleanup --dry-run` → `{dryRun, removed: {worktrees, branches, files, bytes}, kept}`; when `removed` names worktrees or branches, in ask mode ask once with AskUserQuestion, in the person's language, with the counts of `removed` and each entry of `kept` with its `reason`, and on yes run `FORGE swarm cleanup`; in auto, record the decision as `references/decisions.md` says (`point: "other"`, `what: "branch-discard: forge's integrated worktrees and branches"`, `chosen: "swarm cleanup"`, `undo: {"type": "none", "reason": "only integrated branches: their commits are in <current branch>"}`) and run `FORGE swarm cleanup`. Its task worktrees would otherwise stay, and a later run that repeats one of its ids would be refused.

**Resume.** When `FORGE swarm status` shows an active `kind: "ephemeral"` run that you coordinate: `FORGE swarm start --project loose --session <its coordinator> --hook-session <CSID> --kind ephemeral` (no `--tasks`: the run keeps its own), reconcile each task in `running` as `references/resuming.md` step 4 says for a subagents task (stage, agent, round and worktree from `FORGE swarm status`; an agent no longer running is respawned for that step; a verdict already written is not recomputed), then step 3.
