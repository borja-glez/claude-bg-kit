# Tool verification

Read from forge:run (`## Medium` step 3b and step 6 in `SKILL.md`). `FORGE`, `<id>` and the Medium steps cited here mean what that skill says. `<WORK>` is the task's work folder: `.forge/work/<id>` on the Medium path; in an execution, the `work` that `FORGE swarm worktree` printed.

## Before the review

After each answer below, run `verify-plan` again.
- Each `drafts` entry: propose the draft (`FORGE surfaces` shows its body) once; on yes, write `.forge/verify/<name>.md` keeping its `affects` and `tools` header as it is (the body in the user's language) and `FORGE local set surfaces.<name> allowed`; on no, `FORGE surfaces proposed --name <name>`. Commit a new surface with the task's work (plus `.forge/.gitignore` when git does not track it yet).
- Each surface with `permission: changed` (its file changed since the user allowed it): show the change itself, never a summary: its `commits`, then its `diff` verbatim in a ```diff block (`diff` null: `git log -p -n 3 -- .forge/verify/<name>.md`). When `diffTruncated` is true, show the rest from `diffFile` too: never offer «Sí, siempre» on a change the user has not seen whole (no `diffFile`: only the other two options). Ask with AskUserQuestion: `ask.question` with exactly the three `ask.options`, in that order. «Sí, siempre» → `FORGE local set surfaces.<name> allowed --expect <the surface's hash from verify-plan>` (it refuses when the file changed after the question: ask again); «Nunca en este proyecto» → `denied`; «No, esta vez» writes nothing.
- Each surface with `permission: ask`: ask once the same way with its `ask`; allow with `--expect` as above.
- Nobody to ask (`### Unattended` in `references/execution.md`, also auto mode): ask and allow nothing; take that table's safe path (not verified, a `verify-skip`, a question note).
- With `eligible: true`, decide per surface whether it is worth it and the depth (`smoke` or `flow`); a surface without `affects` (`match: null`) only if the diff and its description are related. Each candidate you skip, also when you skip them all: `FORGE log --kind verify-skip --task <id>-<n> --data-file <f>` (`{"surface":"<name>","reason":"<one line>"}`), so the ledger records why (and `FORGE swarm step` does not wait for a verify agent you did not spawn).
- If you verify: spawn `verify` (resolved with `FORGE agents`) **in parallel with the reviewers of Medium step 4**, with the brief, the diff, the chosen surface files, the depth, the `missing` and `unknown` tools (`unknown` may be MCP servers forge cannot see: the agent tries them), review dir `<WORK>/reviews-<n>-<round>/` and evidence dir `<WORK>/evidence/<n>-<round>/` (review-prep's `round`), the limits from `.forge/config.yaml`, the absolute FORGE path and, in a fix round, this brief's previous `verify.json`. Never pass it a reviewer's output, nor its output to a reviewer.

## After the verdict

When `verify.json` exists, close the verification in one call: `FORGE verify-close --task <id>-<n> --dir <WORK>/reviews-<n>-<round> --evidence <WORK>/evidence/<n>-<round>/ --locale <es|en>` (add `--db DB` with a roadmap, and `--cwd <worktree>` for a task in a worktree). It adds each surface's `learned` notes under its Learned/Aprendido heading as `FORGE surfaces learn` does (never add them with Edit: a line added any other way asks for the permission again), stops the processes the agent left running (as `FORGE verify-cleanup` does; it deletes no files, and neither do you), records the result once and prints `{result, learned, proposals, cleanup, evidence: {mode, shots, previous}, commit, say}`. Print its `say`. Then:
- Commit the files in `commit` (the surfaces it changed) with the task's work, or the phase-close commit, so the tree is not left dirty. A `learned` count over 20 for a surface: propose to summarise that section.
- Show its `proposals`; apply one to the surface file with Edit only after the user's yes, then `FORGE local set surfaces.<name> allowed` again (their yes covers that text). Unattended, leave them in a question note.
- **Evidence on the roadmap.** With a roadmap (`state/T`): when `evidence.mode` is `upload`, convert each shot with `oversize: true` to JPEG, upload the `file` of every shot with the Artifact tool (`url: <roadmap url>`, `asset: true`, `file_paths: [...]`, up to 25 per call) and write what it returned, `[{path, id, url}]` (`path` the `file` you uploaded), to `<WORK>/uploads-<n>-<round>.json` with the Write tool (never to `<WORK>/assets.json`: that is forge's own list of the uploads it keeps). Then `FORGE roadmap-doc <id> --assets <WORK>/uploads-<n>-<round>.json` (add `--project <project>` for a plan task; leave out `--assets` when nothing was uploaded: `evidence.mode` `local`, or the upload failed) → `{write, bytes, dropped}`, and apply its `write` (ArtifactData `update` with that `file_path`) pinned to the version of `state/T` (`references/roadmap-writes.md`). It carries the forge block and the evidence of every check of the brief: screenshots with their `url`, checks without one, `unchecked` and the reason; a screenshot not uploaded yet stays `pending: true`, and a later `roadmap-doc` with its upload fills it. Then, once that write landed, delete from the roadmap's assets the ids in `evidence.previous`: only screenshots no check of the task links any more (an earlier run's or an earlier brief's); forge leaves out any it cannot judge. Exit 2 or 3: say it in one line and publish nothing; never compose `evidence` by hand.
