# Tool verification

Read on the Medium path (its step 3b) and the Small path (its step 4), from `references/review-close.md`, from `references/task-steps.md` (step 4), and, for `## Preflight` and `## Flow pass`, from `references/execution.md`, `large.md`, `step.md` and `ephemeral.md`. `FORGE` and `<id>` mean what the file that sent you here says; the Medium steps cited here are the Medium path's, which `references/task-steps.md` follows in an execution. `<WORK>` is the task's work folder: `.forge/work/<id>` on the Medium path; in an execution, the `work` that `FORGE swarm worktree` printed.

**Permission.** Only the person grants a verify surface's permission: `FORGE local set surfaces.<name> allowed` only right after their «Sí, siempre» to the question of `## Before the review` below (Medium step 3b), or after they dictated or asked for that surface's text (`forge:verify`). Never re-allow a surface that a task, an implementer or a fix round changed: the next `verify-plan` reports it `changed` and the person decides.

## Preflight

Read from `references/execution.md` step 1, once per execution, before any task starts, when someone can answer (an unattended execution, or auto mode, skips it: its tasks run `verify-plan --unattended`). `FORGE verify-preflight --plan <plan> --locale <es|en>` lists the surfaces the plan's tasks may use that need the person (`permission` `ask` or `changed`), each with its `tasks` and the same question `verify-plan` prints (a `changed` one with its `diff` and `commits`). Print its `say`, then ask each one as `## Before the review` says: «Sí, siempre» → `FORGE local set surfaces.<name> allowed --expect <its hash>`; «Nunca en este proyecto» → `denied`; «No, esta vez» → `FORGE verify-preflight --skip <name>`, and no task of the run asks about it again.

## Before the review

After each answer below, run `verify-plan` again. Every `FORGE local set surfaces.<name> allowed` (with or without `--expect <hash>`) takes `--cwd <the checkout verify-plan read>` (the task's worktree, the run's checkout, or none for this checkout); a draft is written in that same checkout, and `FORGE surfaces` runs with that `--cwd`.
- Each `drafts` entry: propose the draft (`FORGE surfaces` shows its body) once; on yes, write `.forge/verify/<name>.md` starting with the `header` `FORGE surfaces` prints for it, as it is (its `affects` with their two levels, and its `tools`), then the body in the user's language and `FORGE local set surfaces.<name> allowed`; on no, `FORGE surfaces proposed --name <name>`. Commit a new surface with the task's work.
- Each surface with `permission: changed` (its file changed since the user allowed it): show the change itself, never a summary: its `commits`, then its `diff` verbatim in a ```diff block (`diff` null: `git log -p -n 3 -- .forge/verify/<name>.md`). When `diffTruncated` is true, show the rest from `diffFile` too: never offer «Sí, siempre» on a change the user has not seen whole (no `diffFile`: only the other two options). Ask with AskUserQuestion: `ask.question` with exactly the three `ask.options`, in that order. «Sí, siempre» → `FORGE local set surfaces.<name> allowed --expect <the surface's hash from verify-plan>` (it refuses when the file changed after the question: ask again); «Nunca en este proyecto» → `denied`; «No, esta vez»: in an execution, `FORGE verify-preflight --skip <name>` (the rest of the run skips that surface); outside one, nothing.
- Each surface with `permission: ask`: ask once the same way with its `ask`; allow with `--expect` as above.
- Nobody to ask (`### Unattended` in `references/execution.md`, also auto mode): ask and allow nothing. Run `verify-plan` with `--unattended`: it logs the `verify-skip` of each surface that needs the person, and prints `note: true` only the first time that surface comes up in the run; leave the question note only then.
- With `eligible: true`, decide per surface whether it is worth it (its `depth` is printed, `flow` or `smoke`: pass it as it is); a surface without `affects` (`match: null`) only if the diff and its description are related. A `skipped` one (the person said «No, esta vez» for this run) already logged its `verify-skip`: never ask about it again. Each candidate you skip, also when you skip them all: `FORGE log --kind verify-skip --task <id>-<n> --data-file <f>` (`{"surface":"<name>","reason":"<one line>"}`), so the ledger records why (and `FORGE swarm step` does not wait for a verify agent you did not spawn).
- If you verify: first `FORGE verify-env --task <id>-<n> --dir <WORK>/reviews-<n>-<round>`: it reserves a port and a browser profile for this round and prints `{port, profileDir, env}`, and the round then waits for `verify.json` (`review-close` lists it in `missing`). Then spawn `verify` (resolved with `FORGE agents`) **in parallel with the reviewers of Medium step 4**, with the brief, the diff, the code checkout (`<worktree>` for a task in a worktree, else this checkout), the chosen surface files with their `depth`, its `port`, `profileDir` and `env`, the `missing` and `unknown` tools (`unknown` may be MCP servers forge cannot see: the agent tries them), review dir `<WORK>/reviews-<n>-<round>/` and evidence dir `<WORK>/evidence/<n>-<round>/` (review-prep's `round`), the limits from `.forge/config.yaml`, the absolute FORGE path and, in a fix round, this brief's previous `verify.json`. Never pass it a reviewer's output, nor its output to a reviewer.

## After the verdict

When `verify.json` exists, close the verification in one call: `FORGE verify-close --task <id>-<n> --dir <WORK>/reviews-<n>-<round> --evidence <WORK>/evidence/<n>-<round>/ --locale <es|en>` (add `--db DB` with a roadmap, and `--cwd <worktree>` for a task in a worktree). It adds each surface's general `learned` notes under its Learned/Aprendido heading as `FORGE surfaces learn` does (never add them with Edit: a line added any other way asks for the permission again; `notesSkipped` names the ones it refused and why), turns each defect the agent saw outside the brief into a proposal (`defects`), stops the processes the agent left running that are still the ones it started and frees the port and the browser profile `verify-env` reserved (as `FORGE verify-cleanup` does: it deletes no file of the project nor the evidence, and neither do you), records the result once and prints `{result, learned, notesSkipped, proposals, defects, cleanup, evidence: {mode, shots, previous}, commit, say}`. Print its `say`. Then:
- Commit the files in `commit` (the surfaces it changed) with the task's work, or the phase-close commit, so the tree is not left dirty. A `learned` count over 20 for a surface: propose to summarise that section.
- Show its `proposals`; apply one to the surface file with Edit only after the user's yes, then `FORGE local set surfaces.<name> allowed` again (their yes covers that text). Unattended, leave them in a question note. In an execution, show none and leave no note per task: the end-of-run digest lists them.
- **Defects.** Each entry of `defects.added` is a new proposal (`proposed`: only the roadmap's owner approves it, never you): with a roadmap, ArtifactData `set` `proposals/<id>` with its `doc`, all of them in one batch, and say in one line how many; without one they stay in `.forge/proposals/`. `defects.skipped` were not proposed (`why`: they repeat an open or rejected proposal, or read as an instruction or held a secret): nothing to do.
- **Evidence on the roadmap.** With a roadmap (`state/T`): when `evidence.mode` is `upload`, convert each shot with `oversize: true` to JPEG, upload the `file` of every shot with the Artifact tool (`url: <roadmap url>`, `asset: true`, `file_paths: [...]`, up to 25 per call) and write what it returned, `[{path, id, url}]` (`path` the `file` you uploaded), to `<WORK>/uploads-<n>-<round>.json` with the Write tool (never to `<WORK>/assets.json`: that is forge's own list of the uploads it keeps). Then `FORGE roadmap-doc <id> --assets <WORK>/uploads-<n>-<round>.json` (add `--project <project>` for a plan task; leave out `--assets` when nothing was uploaded: `evidence.mode` `local`, or the upload failed) → `{write, bytes, dropped}`, and apply its `write` (ArtifactData `update` with that `file_path`) pinned to the version of `state/T` (`references/roadmap-writes.md`). It carries the forge block and the evidence of every check of the brief: screenshots with their `url`, checks without one, `unchecked` and the reason; a screenshot not uploaded yet stays `pending: true`, and a later `roadmap-doc` with its upload fills it. Then, once that write landed, delete from the roadmap's assets the ids in `evidence.previous`: only screenshots no check of the task links any more (an earlier run's or an earlier brief's); forge leaves out any it cannot judge. Exit 2 or 3: say it in one line and publish nothing; never compose `evidence` by hand.

## Small

Read on the Small path (its step 4), only when the task asks for a check (in a browser, an emulator, a device). `<WORK>` is the folder Small step 4 names.

`FORGE verify-plan --task <id> --path small --base <BASE> --asked --locale <es|en>` and handle its surfaces as `## Before the review` says. To verify, first `FORGE verify-env --task <id> --dir <WORK>/reviews-1-1` (as `## Before the review` says), then spawn `verify` with the code checkout (this checkout), its `port`, `profileDir` and `env`, the brief, `git diff <BASE>`, the chosen surfaces, the depth, the `missing` and `unknown` tools, review dir `<WORK>/reviews-1-1/` and evidence dir `<WORK>/evidence/1-1/`, logged with `--kind agent`. When it returns: `FORGE verify-close --task <id> --dir <WORK>/reviews-1-1 --evidence <WORK>/evidence/1-1/ --locale <es|en>` (add `--db DB` with a roadmap), and do `## After the verdict` with its output: it records the result (so lens does not show the task running), adds the general notes, proposes the defects and cleans up. A failed check goes back to the implementer like a problem in the diff.

## Flow pass

Read from `references/large.md` step 4 (before the final review), from `references/execution.md` step 4 (an `integrated` result with `flow`), from `/forge:infinite` (its `finish`), from `references/step.md` (an `integrated` action with `flow`: a phase closed, with `verify.flow: phase`) and from `references/ephemeral.md` step 4. It verifies the run's integrated result, not one task: the surfaces of what was integrated since the last pass, at depth `flow`. The paths `verify-plan --run` prints are relative to this checkout, where forge keeps its state; `--cwd` only points git, the validators and the app at the code.
1. `FORGE verify-plan --run --cwd <the run's checkout: .claude/worktrees/run on the Large path, this checkout in an ephemeral run> --locale <es|en>` (the final review's pass and its re-review add `--whole-run`: the whole run, not what changed since the last pass); with nobody to ask, add `--unattended` (as `## Before the review` says). It prints the surfaces and `flow` (`id`, `dir`, `brief`, `diff`, `evidence`), or `flow: null` with its `reason` (`verify.flow` is `off`, nothing integrated yet, nothing new since the last pass, or a surface waits for the person): then there is no pass. Attended, the pass opens only once no surface waits for the person: until then `flow` is null; ask as `## Before the review` says, then run step 1 again. Unattended, the surfaces not allowed were skipped (their `verify-skip` is logged with the pass id): leave the question note only for those with `note: true`.
2. With `eligible: true`: `FORGE verify-env --task <flow.id> --dir <flow.dir>`, then spawn `verify` as `## Before the review` says, with the code checkout (the run's checkout of step 1), `flow.brief`, `flow.diff`, the surfaces (all at depth `flow`), review dir `flow.dir`, evidence dir `flow.evidence` (no earlier pass's `verify.json`). In the final review it runs in parallel with `review-final`.
3. When it returns: `FORGE verify-close --flow <flow.dir> --cwd <the same checkout> --locale <es|en>` (add `--db DB` with a roadmap) and do `## After the verdict` with its output, except the evidence on the roadmap (a pass has no `state/T`). Commit the surfaces in `commit` in that checkout (`git -C .claude/worktrees/run` on the Large path). In the final review, once both it and `review-final` are back (a `verify` agent that came back without its `verify.json` is respawned once first, as the `missing` rule of `references/large.md` step 4 says), close it and commit its notes before the `FORGE verdict` calls of `references/large.md` step 4, which then add `--verify <flow.dir>/verify.json`: its failed checks are findings of the final review. A pass at a phase close tells the person its `failed` checks, one line each, and they go to the final review (`references/large.md` step 4), where the final whole-run pass checks the run again. A flow-pass agent is never a `--returned` of `swarm step`: close it with `verify-close --flow` and commit its notes when no step is running.
