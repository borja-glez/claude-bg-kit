# Superpowers plan

Read from forge:run (`### Superpowers plan` in `SKILL.md`). `FORGE` means what that skill says; the Medium steps cited here are those of its `## Medium`.

`/forge:run --superpowers-plan <f>` runs a plan that `superpowers:writing-plans` wrote: forge executes it, never `superpowers:executing-plans` nor `superpowers:subagent-driven-development`. It always takes the Medium path of `SKILL.md`, with these differences:
1. `<id>` = the plan's file name without its date prefix and `.md` (`2026-10-13-cart-totals.md` → `cart-totals`). `FORGE sp-plan tasks <f>` prints `{plan, tasks}`; exit 2 means it is not a superpowers plan (a task number repeats, or a code fence is left open): tell the user its message, run `FORGE route stage --stage done --session <CSID>` and stop. A task's `done` counts its ticked boxes and superpowers' own ledger (`Task N: complete` lines in `.superpowers/sdd/<plan>/progress.md`, which `superpowers:executing-plans` and `superpowers:subagent-driven-development` write instead of ticking boxes), so a task superpowers already finished is not done again. With every task `done`, say so, run `FORGE route stage --stage done --session <CSID>` and stop. Otherwise run `FORGE route stage --stage handed-off --plan <f> --session <CSID>` (it moves a pending `forge:route` route on with its plan, else changes nothing).
2. Triage with `FORGE triage --task <id> --superpowers-plan <f>`: it reads the pending tasks and their files, and its path is always `medium`. Announce it as `## 1. Triage` in `SKILL.md` says (its **TDD** paragraph applies).
3. The gate's short plan lists the tasks with `done: false`, in order (`N. <title> — <files>`), and you continue unless the user stops you; when they do, run `FORGE route stage --stage done --session <CSID>` and stop.
4. The tasks run **one after another**, in the plan's order, never as an ephemeral execution: a superpowers task builds on the ones before it. Task `N` is brief `N` of `<id>`: `FORGE brief --superpowers-plan <f> --task N > .forge/work/<id>/brief-N.md`, its ids are `<id>-N`, and it goes through Medium steps 2–6 (baseline, implementer, validators, verify, reviewers, verdict) like any Medium brief. Its implementer commits as the task's last step says.
5. When a task is accepted (`done` in step 6): `FORGE sp-plan check <f> --task N` ticks its boxes and prints `{task, checked, recorded}`; a task without boxes is recorded in `.forge/sp-done/` instead and prints `recorded: true`. Exit 2 here means the record could not be written: tell the user in one line and go on. Commit the plan alone only when `checked` is above 0 and git tracks it (`git ls-files --error-unmatch <f>` succeeds): write the message `<plan title>: task N done` to `.forge/work/<id>/commit-N.txt` with the Write tool (the title never goes in a shell string), then `git commit -F .forge/work/<id>/commit-N.txt -- <f>`. When git does not track it (`docs/superpowers/` is often ignored), the ticks stay on disk only. Then the next task.
6. `breaker` or `stalled` with findings that block the work: stop there, since the later tasks build on this one. Tell the user which task stopped and why; its boxes stay unticked. Then `FORGE route stage --stage done --session <CSID>`, so the prompt hook stops reminding the route.
7. At the end, Medium step 7: the phase `done` and the report (one line per task with its verdict and commits), then `FORGE route stage --stage done --session <CSID>`.
