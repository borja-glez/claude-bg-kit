# Large

Read from forge:run (`## Large` in `SKILL.md`). `FORGE`, `<id>` and the Medium steps cited here mean what that skill says.

Subsystem, architecture, much ambiguity or risk, or a greenfield project. Gate: **mandatory approval** of the design.
1. **Design.** Log the phase `design` (and `plan` when step 2 starts, so lens shows where the run is). **From a spec:** with `--from-spec <f>`, run `/waypoint:design new --from <f>` instead of writing the design from scratch. Without it, before writing a design from scratch, run `FORGE sp-specs` (not in auto: there a spec is used only with `--from-spec`, when the route chose it, since the offer is a question) (specs superpowers wrote here in the last 14 days that no design imported yet): when it lists any, ask once with AskUserQuestion «¿Parto del spec `<path>` (<title>)?», in the user's language, the newest first plus «No, un diseño nuevo»; on a yes, `/waypoint:design new --from <path>`; on «No», `FORGE sp-specs --decline <path>`, so that spec is not offered again. Otherwise run `/waypoint:design new` to write `docs/waypoint/<project>/design.md`: it publishes v1, offers the first critique round and ends the turn. **In auto**, the project is the one named at launch for the final-merge question (`references/autonomy.md`): give that name to `/waypoint:design new`, with or without `--from` (the name the user named, which wins over a spec's file name), so the design is `docs/waypoint/<that project>/design.md`. A design under another name drops the launch yes: `FORGE swarm start` prints `mergeRefused` `other project`, the run does not merge by itself, and the final merge is asked again at the end (`FORGE swarm merge` prints `needs-authorization`). In ask mode the user decides every round, apply, interview and the approval (`/waypoint:design round`, `apply`, `approve`): never launch a round they did not ask for. Wait until the user approves it (`/waypoint:design approve`). Never approve it yourself unless autonomy is auto: then run the design loop of `references/autonomy.md`, which ends with `/waypoint:design approve --auto`. Under forge, `approve` runs only its steps 1–3 (approve, snapshot, publish); its step 4 (`waypoint:plan`) is replaced by step 2 below. That approval also covers the private roadmap publish that `/waypoint:plan` does. Once approved (the project id is known), write `.forge/work/<project>/run.json` with `{ "base": "<git rev-parse HEAD>" }` only if that file does not exist yet; never overwrite it (on resume it keeps the run's original base).
2. **Plan.** Get waypoint's CLI path with `FORGE waypoint-cli`, and the fixed cost of a task in this repository with `FORGE stats --json > .forge/work/<project>/stats.json` (an empty ledger gives empty stats: the planner then assumes its defaults). Spawn `forge-planner` with the design path, the plan path `docs/waypoint/<project>/plan.yaml`, the user's language, that CLI path, the repo root and that stats file. Show the user the phase outline it replies with and ask once for confirmation (as waypoint's plan step does) (in auto, confirm it without asking and record `plan-confirm` with `undo` `{"type": "plan-edit", "project": "<project>", "tasks": [<the ids it added>]}`). If the design's `start_prompt` contains `<track>`, rewrite it in `design.md` yourself: replace `<track>` with the id of the plan's first track, as `waypoint:plan` does when `plan.yaml` does not exist yet (small commit, no new design version). Then re-run `design-page` and re-publish to the design's `artifact` URL, as the `waypoint:plan` skill's `start_prompt` paragraph says. Then run `FORGE config get evidence` and `/waypoint:plan` (`/waypoint:plan assets` when it printed `upload`: the roadmap will carry forge's verification screenshots): plan.yaml now exists, so it validates, publishes the live roadmap and syncs it. Print what that skill hands over, as it is: the sharing notice of its publish (when the roadmap carries forge's screenshots it becomes internal to the organization) and its report (the roadmap URL and the number of tasks, phases and tracks), adding that forge runs the tasks next; put them in the message of step 3's mode question, or right before the execution starts.
3. **Tasks.** Run `FORGE swarm propose --plan <plan> --locale <es|en>` and print its `say` as it is (the plan's waves, its longest chain and the zones that serialize it). Then ask the start questions in one AskUserQuestion, in the person's language, only those that apply and at most four (none in auto: `references/autonomy.md` takes `recommended` and records `mode`):
   1. **Mode**, unless the user already said how ("en enjambre", "con sesiones", "con subagentes", "en paralelo", "secuencial"), `configured` is not null, or `recommended.parallel` is 1 (then say in one line that it runs one task at a time, and why): the recommended option first, labelled "(Recomendado)", with its `reasons`, then "Enjambre de sesiones" (you can talk to each task's session; useful in very long plans) and "Secuencial". "Enjambre de sesiones" is mode `sessions`: `references/execution.md` step 1 runs `FORGE swarm start … --mode sessions` and each task runs in its own background session (a run member, forge:member; **Run members.** in `SKILL.md`); the other options are mode `subagents`. N is the user's `--parallel` if given, else `recommended.parallel`.
   2. **Final merge:** first run `FORGE authorize merge-on-finish --run <runId> --branch <current branch> --locale <es|en>` (`<runId>`: the one `swarm propose` printed); this question is its `ask`, exactly as printed (question, header and options, «No» first). forge's hook records the person's answer, and only that recorded yes lets the run merge by itself at the end.
   3. **Where:** «En una sesión limpia» (recommended: the coordinator starts without the design's context) or «Aquí».
   4. Only with `mostlySerial`: «Replanificar para ganar paralelismo» or «Seguir». «Replanificar»: spawn `forge-planner` again with the design, the plan, the stats file of step 2 and `propose`'s output, asking it to «split shared test files and shorten chains; keep the ids of tasks that stay»; then `/waypoint:plan` and `propose` again, without asking again.

   «En una sesión limpia»: write `.forge/work/<project>/launch.json` with the Write tool, `{"mode", "parallel", "mergeOnFinish", "autonomy", "locale", "runId", "at": NOW}` (`mergeOnFinish`: whether the person chose the yes; `runId`: `swarm propose`'s), tell the person in their language «El plan está listo. Para que la coordinadora arranque sin el contexto del diseño: `/clear` y después `/forge:run --execute <project>`», and stop. «Aquí», and always in auto: read `references/execution.md` now and follow it with the chosen mode and N (N = 1 is the sequential path), and come back to step 4 when it finishes. The coordinator always runs in the main checkout, in a session the person can talk to.
4. **Final review.** When every task of the run is done (or at a phase close the user asks to review). Validation here includes the e2e and bench validators when the project has them: forge detects them; list them in `.forge/config.yaml` only when detection misses them.
   - `FORGE validate --final --task <project>-final --cwd .claude/worktrees/run > .forge/work/<project>/final-validators.json`.
   - `git -C .claude/worktrees/run diff <base>..HEAD > .forge/work/<project>/final.patch`, with `base` from `.forge/work/<project>/run.json`. The run worktree holds the whole run on `forge/run-<project>`; the final review is of all of it.
   - The final review stays a full review (no review-prep, no delta): spawn the `review-final` agent (resolved with `FORGE agents`; no `effort` override, its frontmatter is xhigh) with the design path, the plan path, that diff and the final validators file, output dir `.forge/work/<project>/final-1/`. Then `FORGE verdict --task <project>-final --dir .forge/work/<project>/final-1 --validators .forge/work/<project>/final-validators.json`. If its `invalid` or `incomplete` names the reviewer (`incomplete`: its file is a draft with `complete: false`), respawn it once with the same inputs (it picks up its own draft) and run the verdict again; still invalid or incomplete after that: keep the result. Act on the verdict's `action` (not the reviewer's own `verdict`).
   - If the action is `fix` or `redo` (a whole run is never redone: `redo` is treated as `fix`): one fix by `impl-heavy` with the final review JSON as its brief, the absolute path of the run worktree (it works and commits there, on `forge/run-<project>`), report path `.forge/work/<project>/final-fix.txt`, task id `<project>-final`. Then the re-review, on fresh inputs: `FORGE validate --final --task <project>-final --cwd .claude/worktrees/run > .forge/work/<project>/final-validators-2.json`, `git -C .claude/worktrees/run diff <base>..HEAD > .forge/work/<project>/final-2.patch` (same `base` from `run.json`), spawn `review-final` again with the design path, the plan path, `final-2.patch` and `final-validators-2.json`, output dir `.forge/work/<project>/final-2/`, then `FORGE verdict --task <project>-final --dir .forge/work/<project>/final-2 --validators .forge/work/<project>/final-validators-2.json` (same `invalid`/`incomplete` rule). Whatever remains goes to the user as rulings; no second fix.
   - The final review covers only what is integrated into the run branch. With the verdict, list to the user the task branches not integrated yet (`git branch --list 'task/*' --no-merged forge/run-<project>`): their work was not reviewed.
5. Log the phase `done`, then report: the roadmap URL, tasks done, verdict scores, rulings, task branches not integrated, and the automatic decisions (`references/decisions.md`, both `--task <project>` and `--run <runId>`).

### From a spec

Read from forge:run (**From a spec.** in `## 1. Triage`), before its step 1, when `/forge:run` starts with `--from-spec <f>`. With or without task text, write the spec's title and the first paragraph of its purpose section to `.forge/work/<id>/task.txt` (`<id>` from the spec's file name, as `waypoint:design new --from` derives the project). The path is Large whatever `FORGE triage` prints: log the raise as the ratchet says (`{"path":"large"}`). Run `FORGE route stage --stage handed-off --session <CSID>` (it moves a pending `forge:route` route on, else changes nothing), and `FORGE route stage --stage done --session <CSID>` with the report that closes the work (step 5).
