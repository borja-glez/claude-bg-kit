# Large

Read from forge:run (`## Large` in `SKILL.md`). `FORGE`, `<id>` and the Medium steps cited here mean what that skill says.

Subsystem, architecture, much ambiguity or risk, or a greenfield project. Gate: **mandatory approval** of the design.
1. **Design.** Log the phase `design` (and `plan` when step 2 starts, so lens shows where the run is). **From a spec:** with `--from-spec <f>`, run `/waypoint:design new --from <f>` instead of writing the design from scratch. Without it, before writing a design from scratch, run `FORGE sp-specs` (not in auto: there a spec is used only with `--from-spec`, when the route chose it, since the offer is a question) (specs superpowers wrote here in the last 14 days that no design imported yet): when it lists any, ask once with AskUserQuestion «¿Parto del spec `<path>` (<title>)?», in the user's language, the newest first plus «No, un diseño nuevo»; on a yes, `/waypoint:design new --from <path>`; on «No», `FORGE sp-specs --decline <path>`, so that spec is not offered again. Otherwise run `/waypoint:design new` to write `docs/waypoint/<project>/design.md`: it publishes v1, offers the first critique round and ends the turn. In ask mode the user decides every round, apply, interview and the approval (`/waypoint:design round`, `apply`, `approve`): never launch a round they did not ask for. Wait until the user approves it (`/waypoint:design approve`). Never approve it yourself unless autonomy is auto: then run the design loop of `references/autonomy.md`, which ends with `/waypoint:design approve --auto`. Under forge, `approve` runs only its steps 1–3 (approve, snapshot, publish); its step 4 (`waypoint:plan`) is replaced by step 2 below. That approval also covers the private roadmap publish that `/waypoint:plan` does. Once approved (the project id is known), write `.forge/work/<project>/run.json` with `{ "base": "<git rev-parse HEAD>" }` only if that file does not exist yet; never overwrite it (on resume it keeps the run's original base).
2. **Plan.** Get waypoint's CLI path with `FORGE waypoint-cli`. Spawn `forge-planner` with the design path, the plan path `docs/waypoint/<project>/plan.yaml`, the user's language, that path and the repo root. Show the user the phase outline it replies with and ask once for confirmation (as waypoint's plan step does) (in auto, confirm it without asking and record `plan-confirm` with `undo` `{"type": "plan-edit", "project": "<project>", "tasks": [<the ids it added>]}`). If the design's `start_prompt` contains `<track>`, rewrite it in `design.md` yourself: replace `<track>` with the id of the plan's first track and append ` — forge drives this session (forge:run Large loop)`, so the default becomes `/waypoint:work <track id> — forge drives this session (forge:run Large loop)` and parallel sessions launched from it run the forge loop too (`/waypoint:launch` adds the forge suffix to them when the design's `start_prompt` carries it) (small commit, no new design version). Then re-run `design-page` and re-publish to the design's `artifact` URL, as the `waypoint:plan` skill's `start_prompt` paragraph says. Then run `/waypoint:plan`: plan.yaml now exists, so it validates, publishes the live roadmap and syncs it. Print what that skill hands over, as it is: the sharing notice of its publish (when the roadmap carries forge's screenshots it becomes internal to the organization) and its report (the roadmap URL and the number of tasks, phases and tracks), adding that forge runs the tasks next; put them in the message of step 3's mode question, or right before the execution starts.
3. **Tasks.** **Mode.** Run `FORGE swarm propose --plan <plan>`. Do not ask when the user already said how ("en enjambre", "con sesiones", "con subagentes", "en paralelo", "secuencial"), when `configured` is not null, when autonomy is auto (take `recommended` and record `mode`), or when `recommended.parallel` is 1 (then say in one line that it runs one task at a time, and why). Otherwise ask once with AskUserQuestion: the recommended option first, labelled "(Recomendado)", with its `reasons`, then "Enjambre de sesiones" (you can talk to each task's session; useful in very long plans) and "Secuencial". "Enjambre de sesiones" is mode `sessions`: `references/execution.md` step 1 runs `FORGE swarm start … --mode sessions` and each task runs in its own background session (a run member, below); the other options are mode `subagents`. N is the user's `--parallel` if given, else `recommended.parallel`. Then read `references/execution.md` and follow it with the chosen mode and N (N = 1 is the sequential path), and come back to step 4 when it finishes.
4. **Final review.** When every task of the run is done (or at a phase close the user asks to review). Validation here includes the e2e and bench validators when the project has them: forge detects them; list them in `.forge/config.yaml` only when detection misses them.
   - `FORGE validate --final --task <project>-final --cwd .claude/worktrees/run > .forge/work/<project>/final-validators.json`.
   - `git -C .claude/worktrees/run diff <base>..HEAD > .forge/work/<project>/final.patch`, with `base` from `.forge/work/<project>/run.json`. The run worktree holds the whole run on `forge/run-<project>`; the final review is of all of it.
   - The final review stays a full review (no review-prep, no delta): spawn `review-correctness` in final review mode, passing the Agent tool's `effort: xhigh` (its frontmatter says high), with the design path, the plan path and that diff, output dir `.forge/work/<project>/final-1/`. Then `FORGE verdict --task <project>-final --dir .forge/work/<project>/final-1 --validators .forge/work/<project>/final-validators.json` and act on the verdict's `action` (not the reviewer's own `verdict`).
   - If the action is `fix` or `redo` (a whole run is never redone: `redo` is treated as `fix`): one fix by `impl-heavy` with the final review JSON as its brief, the absolute path of the run worktree (it works and commits there, on `forge/run-<project>`), report path `.forge/work/<project>/final-fix.txt`, task id `<project>-final`. Then the re-review, on fresh inputs: `FORGE validate --final --task <project>-final --cwd .claude/worktrees/run > .forge/work/<project>/final-validators-2.json`, `git -C .claude/worktrees/run diff <base>..HEAD > .forge/work/<project>/final-2.patch` (same `base` from `run.json`), spawn `review-correctness` in final review mode (again `effort: xhigh`) with the design path, the plan path and `final-2.patch`, output dir `.forge/work/<project>/final-2/`, then `FORGE verdict --task <project>-final --dir .forge/work/<project>/final-2 --validators .forge/work/<project>/final-validators-2.json`. Whatever remains goes to the user as rulings; no second fix.
   - The final review covers only what is integrated into the run branch. With the verdict, list to the user the task branches not integrated yet (`git branch --list 'task/*' --no-merged forge/run-<project>`): their work was not reviewed.
5. Log the phase `done`, then report: the roadmap URL, tasks done, verdict scores, rulings, task branches not integrated, and the automatic decisions (`references/decisions.md`, both `--task <project>` and `--run <runId>`).
