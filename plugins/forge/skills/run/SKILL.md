name: run
description: Do a software task with the forge method - triage by size, the right model per step, tool-first validation and weighted independent review; on the Large path it coordinates an execution that drives each task through subagents or background sessions on a run branch (--parallel N, default 3). Several independent requests in one message, and the independent briefs of a Medium task, run in parallel as an ephemeral execution integrated into the current branch. Use for any coding task the user asks to "forge", or via /forge:run <task> [--parallel N]; `--from-spec <spec>` starts the Large path from a superpowers spec, `--superpowers-plan <plan>` runs a superpowers plan task by task; a session launched for one task of an execution runs it as a run member, and /forge:run --join joins a running execution as a manual member.

# forge: run a task

`FORGE` below means `node "${CLAUDE_PLUGIN_ROOT}/dist/forge.cjs"`. Work files go in `.forge/work/<task-id>/` (task id: a short kebab-case slug of the task, or the waypoint task id when one is in progress). Speak to the user in their language; keep internal names in English.

Ids: `<id>` is the task id, used for triage and phase logs. Each brief of a Medium or Large task gets its own id `<id>-<n>`, used for `validate`, `verdict` and `round` (round counting is per brief) and as the task id you hand to the implementer; for Large, `<id>` is the plan task id. Before spawning agents, resolve `${CLAUDE_PLUGIN_ROOT}` to an absolute path and give subagents the absolute path of `forge.cjs`, never the variable.

Never put user text or JSON inside a shell string. Write the task text to `.forge/work/<id>/task.txt` and any log data to a JSON file (e.g. `.forge/work/<id>/log.json`), then pass the file flags (`--text-file`, `--data-file`).

Rules for every path:
- Irreversible or outward actions (delete, merge into main, publish) always need the user's approval; never push without being asked.
- Before you start, run `git status --porcelain`. If the tree has changes that are not part of this task (the user's own work, an earlier task left uncommitted), ask the user whether to commit, stash or leave them before you go on; never commit, stash or discard them on your own. forge's own files under `.forge/` do not count.
- Always name the agent when you spawn one (subagent type `forge:<agent>`); never let work inherit your own model. Roles (`impl`, `review-security`, ...) map to agent names through `FORGE agents` (it applies the profile in `.forge/config.yaml`).
- The implementer **tier ladder**, in roles: `mech` -> `impl-light` -> `impl` -> `impl-heavy`. "One tier up" is the next role on it, resolved to an agent with `FORGE agents`; above `impl-heavy` stay on `impl-heavy` and tell the user at the end.
- `forge-fable` is used only when the user explicitly asks for Fable.
- Change the project's files with the Edit and Write tools, never with `sed -i`, `awk`, `perl -i` or by rewriting them through shell redirection: those rewrite whole files and can change their line endings (CRLF on Windows), which turns a one-line change into a whole-file diff. Saving a command's output to forge's own work files (`FORGE validate ... > .forge/work/...`, `git diff ... > .forge/work/...`) is fine and stays as the steps say. This holds on every OS and in every path, also when you implement yourself.
- Hand over briefs, diffs and reports as files. No narration, no "shall I continue?".
- Record each phase with `FORGE log --kind phase --task <id> --data-file <file>` (file: `{"phase":"<name>","brief":<n>,"base":"<BASE sha>"}`, so resuming knows the brief and the base), and each agent you spawn with `--kind agent` (file: `{"agent":"<name>","role":"<role>"}`). Trivial skips this logging: triage and validate are enough.

## Decisions

A decision you take in place of the user because nobody is there to ask (an unattended execution: the safe paths of `### Unattended`) is recorded with `FORGE decision add --data-file <f>`, never with the generic `FORGE log` (it skips the checks and the summary lens reads). Attended rulings stay `FORGE log --kind ruling` and go in the report's rulings, as the paths below say: the user is there and sees them. Write the file with the Write tool in `.forge/work/<id>/`:

`{"point": "<route|triage|design-apply|design-approve|plan-confirm|mode|ruling|safe-path|other>", "what": "<one line>", "chosen": "<the option taken>", "alternatives": ["<the others>"], "why": "<one line>", "by": "unattended", "revert": "<how to undo it, in the user's language>", "undo": <one of the shapes below>, "task": "<id>"}`

`undo` is `{"type": "git-revert", "base": "<sha>", "head": "<sha>", "cwd": "<dir, when the commits are not in this checkout>"}`, `{"type": "design-reopen", "project": "<id>"}`, `{"type": "plan-edit", "project": "<id>", "tasks": ["<the ids it added>"]}`, `{"type": "branch-discard", "branch": "<name>"}` or `{"type": "none", "reason": "<why it cannot be undone>"}`. Always write `revert`: one sentence in the user's language on how to undo it, or, when nothing can, why not and what to do instead (then `undo` is `{"type": "none", "reason": "<the same reason>"}`). It prints the event with its number `n`; during an execution it carries the run's `runId`. Exit 2 means the file is wrong: fix what the message names and run it again.
- **With a roadmap** (`artifacts.roadmap` in a `docs/waypoint/*/plan.yaml`): also ArtifactData `set` `notes/<EID>` (`EID` = `node "<WP>" event-id <SID>`, `WP` = `FORGE waypoint-cli`, `SID` = this session's waypoint id, or `main`) `{ts: NOW, type: "decision", author: "session:<SID>", text: "<what> → <chosen>: <why>", taskId: "<T, when there is one>", decision: {point, what, chosen, alternatives, why, revert, auto: true}}`, the texts in the user's language.
- **Without a roadmap:** when the task closes, `FORGE decision md --scope <scope> --locale <es|en>` (the user's language: `es` for Spanish, `en` for anything else; `<scope>`: the execution's `runId`, else the task id without a brief suffix `-<n>`). It writes `docs/forge/decisions/<scope>.md` only when the scope has automatic decisions and prints `written` and `path`; commit that file with the task's work, or in a small `forge: decisions` commit right after it. In a plan execution the work is on the run branch: run it with `--cwd .claude/worktrees/run` before `FORGE swarm merge` (Execution step 7) and commit the file there (`git -C .claude/worktrees/run`), so it lands with the run. An ephemeral execution writes it in this checkout after its last integration.
- **Report.** Every report that closes work (Medium step 7, Large step 5, Execution step 7, Ephemeral execution step 4) ends with a section «Decisiones automáticas» (in the user's language) built from `FORGE decision list --auto --task <id>` (`--run <runId>` for an execution): one line per decision, `n. <what> → <chosen> (<why>) · revertir: <revert>`. Leave the section out when the list is empty. The user lists them with `/forge:decisions` and undoes one with `/forge:decisions revert <n>`.

## 1. Triage

Write the task text to `.forge/work/<id>/task.txt` and run `FORGE triage --task <id> --text-file .forge/work/<id>/task.txt`. It returns `path`, `files`, `sensitive`, `greenfield`, `validators`, `reasons`. Add your own judgement of ambiguity and risk: you may raise the path, never lower it below the CLI's. The CLI only counts files and words, so read the code the task touches and **raise to at least Medium** (log it as below) when the task:
- changes behaviour callers rely on: new errors or rejected inputs, a changed signature, different return values;
- bundles several independent changes;
- adds new behaviour with its tests, rather than a mechanical or one-spot fix.

Announce in one line: path, why (name the reason when you raised it, e.g. "Medium: changes the contract of addItem"), and that the user can correct it. The **ratchet**: during the task the path can only go up (e.g. small -> medium when the change turns out to touch a sensitive zone); log the change with `FORGE log --kind triage --task <id> --data-file <file>` (file: `{"path":"<new path>"}`). Once you raise the path, follow that path: re-running `FORGE triage` for the same task keeps the highest path already logged, and you never go back to a lower one. The triage output's `implementer` (`role`, `agent`, `self`, `why`) says who implements this size: name it in the same line, as printed ("Small → <implementer.agent>: <why>"). Pass `--batch` to `FORGE triage` when the task is one request of several in the same message (see `### Ephemeral execution`).

If the triage output's `new` list (validator names) is not empty, announce each one in the same message with its `cmd` from the output's `catalog` ("new validator e2e: `npx playwright test`"); do not ask anything.

**TDD.** Run `FORGE tdd` once per task. When its `line` is not null, every implementer brief you write by hand (Small, Medium, ephemeral and execution briefs) ends with that line as printed (it starts `TDD: required`; `FORGE brief` adds it itself), and when you spawn `review-correctness` for such a brief you also give it the implementer's report path. When `tdd` is `superpowers` and `line` is null, say in the triage line that superpowers is not installed (or has no `test-driven-development` skill) and that the task goes on without TDD.

If the user, at any point, explains how to check something of the project ("para probar X usa Y"), follow the `forge:verify` skill: write or update `.forge/verify/<name>.md` without asking.

If a waypoint task is in progress (the waypoint work skill claimed it), use its id as the task id.

## Trivial

One file, obvious change. No gate.
1. Implement it yourself.
2. `FORGE validate --affected <file> --task <id>`; fix until it passes (stop after 3 tries and report).
3. Report in two lines: what changed, validation result.

## Small

<= 3 files, no ambiguity, no sensitive zone. No gate, no reviewers.
0. Record `BASE=$(git rev-parse HEAD)`.
1. A Small task is **always delegated**: write `.forge/work/<id>/brief-1.md` (what to change, the files, the exact values) and spawn the agent that the triage output's `implementer.agent` names, as printed (the `mech` role for mechanical work — renames, data, code already written —, the `impl-light` role otherwise; the profile picks the agent) with the brief, the report path `.forge/work/<id>/report-1.txt` and the absolute FORGE path; log it with `--kind agent`. The only exception: the whole change is already in your context (you read it in this turn) and it is 10 lines or fewer. Then do it yourself and say so in the triage line ("Small: lo hago yo, el cambio ya está en contexto").
2. `FORGE validate --all --path small --task <id>`.
3. Read the real `git diff $BASE` yourself and fix what you find.
4. Report in two lines.

## Medium

Several files or some design; moderate risk. Gate: show a short plan (<= 10 lines: tasks, files, validators) and **continue** unless the user stops you.
1. If `validators` is empty, the first task creates minimal tests for what you will touch.
2. For each task, write `.forge/work/<id>/brief-<n>.md` (requirements, exact values, files) and record `BASE=$(git rev-parse HEAD)`. Then record what already fails on BASE, before any change: `FORGE validate --all --path medium --base $BASE --base-run --task <id>-<n> > .forge/work/<id>/baseline-<n>.json` (once per brief; fix rounds reuse it; on the Large path use `--path large`). A failure that BASE already had (a build that needs a file a later task creates) is not this brief's fault and does not count. Spawn the `impl` agent (or `impl-heavy` for delicate or important work) with the brief, a report path `.forge/work/<id>/report-<n>.txt`, the task id `<id>-<n>` and the absolute `FORGE` command. If the implementer could not write the report file, save the report from its reply (after `--- report ---`) to that path yourself. **Briefs in parallel.** When the short plan has two or more briefs and at least two of them neither depend on each other nor share a file, run the briefs as an ephemeral execution (`### Ephemeral execution`, one loose task per brief: id `<id>-<n>`, path `medium`, zones the brief's files, `depends_on` the briefs it needs) instead of one after the other. A brief that depends on another starts once that one is integrated. Each brief's work files are then in `.forge/work/<id>-<n>/` (its loose task's directory: `brief-1.md`, baseline, validators, reviews). When that execution ends, go on with step 7 below.
3. Run `FORGE validate --all --path medium --base $BASE --baseline .forge/work/<id>/baseline-<n>.json --task <id>-<n> > .forge/work/<id>/validators-<n>.json`. It marks a failure BASE already had `preexisting: true`, and the verdict leaves it out; a test runner that finds no tests passes as `skipped: "no-tests"`.
3b. **Tool verification.** `FORGE verify-plan --task <id>-<n> --path medium --base $BASE` (add `--asked` when the task text asks to check it in a browser, emulator or device).
   - For each `drafts` entry: propose the draft (`FORGE surfaces` shows its body) once; with a yes, write `.forge/verify/<name>.md` keeping the draft's `affects` and `tools` header from `FORGE surfaces` as it is (the body in the user's language) and `FORGE local set surfaces.<name> allowed`; with a no, `FORGE surfaces proposed --name <name>`. Then run `verify-plan` again.
   - For each surface with `permission: changed`: its file changed since the user allowed it (someone edited the instructions, e.g. in a commit or a PR). Show what changed, summarised: `git diff -- .forge/verify/<name>.md` (uncommitted changes) and `git log -p -n 3 -- .forge/verify/<name>.md` (committed ones). Then ask "¿Verifico <name> con estas instrucciones? sí, siempre / no, esta vez / nunca en este proyecto": "sí, siempre" → `FORGE local set surfaces.<name> allowed` (it stores the new content's hash); "nunca" → `denied`; "no, esta vez" writes nothing. After the answer run `verify-plan` again.
   - For each surface with `permission: ask`: ask once — "¿Verifico <name> (<its title>, con <tools>)? sí, siempre / no, esta vez / nunca en este proyecto". "sí, siempre" → `FORGE local set surfaces.<name> allowed`; "nunca" → `denied`; "no, esta vez" writes nothing. Then run `verify-plan` again.
   - With `eligible: true`, decide per surface whether it is worth it and the depth (`smoke` or `flow`). A surface without `affects` (`match: null`) is verified only if the diff and its description are related. For each candidate you skip: `FORGE log --kind verify-skip --task <id>-<n> --data-file <f>` (`{"surface":"<name>","reason":"<one line>"}`). This also holds when you skip every surface of an eligible plan: log one `verify-skip` per surface, so the ledger records why nothing was verified.
   - If you verify: spawn `verify` (resolved with `FORGE agents`) **in parallel with the reviewers in step 4**, with the brief, the diff, the chosen surface files, the depth, the `missing` tools, review dir `.forge/work/<id>/reviews-<n>-<round>/` and evidence dir `.forge/work/<id>/evidence/<n>-<round>/` (`<round>` as step 4 defines it: 1 + the `round` value of the previous `FORGE round` call for this brief; 1 at first), the limits from `.forge/config.yaml`, the absolute FORGE path and, in a fix round, the previous `verify.json` of this brief. Never pass it a reviewer's output, nor its output to a reviewer.
4. `git diff $BASE..HEAD > .forge/work/<id>/diff-<n>.patch`. Spawn the `review-correctness` agent, and also `review-security` when `sensitive` is not empty (and `review-perf` for performance tasks), each with the brief, the diff, the validators file and the output dir `.forge/work/<id>/reviews-<n>-<round>/` (round = 1 + the `round` value of the previous `FORGE round` call for this brief; 1 at first). They run independently: spawn them in parallel and never pass one reviewer's output to another. Reviewers set `"approach": "wrong"` in their JSON when the change should be redone with another approach rather than patched.
5. Before calling the verdict, check that every spawned reviewer wrote its file (`correctness.json`, `security.json`, `perf.json`, and `verify.json` when `forge-verify` was spawned) in the review dir. `FORGE verdict` exits 2 when the dir holds none of them: if a reviewer did not write its file, resume it or respawn it; do not call the verdict without files. Check this each time you are told a reviewer finished, not only when the last one does: a reviewer that finished without its file is respawned at once, and you never end the turn while a spawned reviewer has neither its file nor a running agent (nothing would wake you).
6. `FORGE verdict --task <id>-<n> --dir .forge/work/<id>/reviews-<n>-<round> --validators .forge/work/<id>/validators-<n>.json` (add `--sensitive` when sensitive, `--perf` for performance tasks). If a reviewer in its output has `invalid: true`, respawn that reviewer once with the same inputs and the same dir and run the verdict again on that dir before trusting it (a verdict re-run on the same dir counts once). `invalid: true` with `dropped: 0` means its JSON was unusable and it abstained; with `dropped` > 0 only some findings were unusable: the review keeps its verdict and still scores. If it is still invalid after the respawn, keep the result as it is; when findings were dropped, read the reviewer's raw JSON file and record the dropped findings as a ruling (`FORGE log --kind ruling --task <id>-<n> --data-file <file>`, file: `{"dropped":[...]}`). Then `FORGE round --task <id>-<n> --path medium` and follow `next`. **Findings to send** below means the critical and important findings of the verdict plus the `failures` of every validator with `ok: false` and no `preexisting` in `validators-<n>.json`.
   - `done`: next task. Minor findings go to the ledger: `FORGE log --kind ruling --task <id>-<n> --data-file <file>` (file: `{"minor":[...]}`).
   - `resume`: send the findings to the same implementer (resume it), then repeat from step 3.
   - `fresh-stronger`: spawn a fresh implementer one tier up the ladder with the brief, the report and the findings to send, then repeat from step 3.
   - `redo`: undo the attempt without rewriting history: `git revert --no-edit $BASE..HEAD` (skip it when HEAD is still `BASE`), then a fresh implementer starts again from the brief with a different approach; repeat from step 3.
   - `breaker` or `stalled`: stop the loop. If what is open blocks the work, tell the user and ask; otherwise record the open findings as a ruling (`FORGE log --kind ruling --data-file <file>`) and continue, telling the user at the end.
   - `tierUp: true` (from round 3) and `fresh-stronger` mean the same single step up the ladder, not two: the implementer of that round is one tier above the one before it. With next = `redo` and `tierUp: true`, the fresh implementer is that one tier up.
   After the verdict, when `verify.json` exists:
   - Append its `learned` notes per surface: write a JSON array of the `note` strings for that surface to a file and run `FORGE surfaces learn --name <surface> --notes-file <f> --heading Aprendido` (or `Learned` in English); never add Learned notes with Edit, since `surfaces learn` keeps the surface's permission valid. If the returned `count` is over 20, propose to the user to summarise that section. The appended surface file is part of the task's changes: commit it with the task's work (or in the phase-close commit), so the tree is not left dirty.
   - Show its `proposals` to the user; apply a proposal to the surface file with Edit only after a yes, and then run `FORGE local set surfaces.<name> allowed` again.
   - Run `FORGE verify-cleanup --dir .forge/work/<id>/evidence/<n>-<round>/` (it stops anything the agent left running).
   - **Evidence on the roadmap.** When the task has a roadmap (`state/T`) and `.forge/config.yaml` has `evidence: upload` (the default): convert any screenshot over 2 MB to JPEG, upload the screenshots of this pass with the Artifact tool (`url: <roadmap url>`, `asset: true`, `file_paths: [...]`, up to 25 per call), then ArtifactData `update state/T` pinned to its version with `evidence: {surfaces, result, passed, total, local: "<evidence dir>", shots: [{url, id, surface, check, ok, expected, observed}]}`. Delete from the roadmap's assets the ids of the previous pass of this task. If the upload fails, write `evidence` without `url`/`id` and with `pending: true`, and retry on the next update of the task. With `evidence: local` or no roadmap, write `evidence` without `url`/`id`.
   A fail of `verify` is a finding like any other: its failed checks are in the verdict's critical/important lists and go in **Findings to send**.
7. Log the phase `done` (same file shape, with the last brief number), so the roadmap and lens show the run as finished. Then report: tasks, commits, verdict scores, rulings and the automatic decisions (`## Decisions`).

### Superpowers plan

`/forge:run --superpowers-plan <f>` runs a plan that `superpowers:writing-plans` wrote: forge executes it, never `superpowers:executing-plans` nor `superpowers:subagent-driven-development`. It always takes the Medium path above, with these differences:
1. `<id>` = the plan's file name without its date prefix and `.md` (`2026-10-13-cart-totals.md` → `cart-totals`). `FORGE sp-plan tasks <f>` prints `{plan, tasks}`; exit 2 means it is not a superpowers plan (a task number repeats, or a code fence is left open): tell the user its message and stop. A task's `done` counts its ticked boxes and superpowers' own ledger (`Task N: complete` lines in `.superpowers/sdd/<plan>/progress.md`, which `superpowers:executing-plans` and `superpowers:subagent-driven-development` write instead of ticking boxes), so a task superpowers already finished is not done again. With every task `done`, say so and stop.
2. Triage with `FORGE triage --task <id> --superpowers-plan <f>`: it reads the pending tasks and their files, and its path is always `medium`. Announce it as `## 1. Triage` says (its **TDD** paragraph applies).
3. The gate's short plan lists the tasks with `done: false`, in order (`N. <title> — <files>`), and you continue unless the user stops you.
4. The tasks run **one after another**, in the plan's order, never as an ephemeral execution: a superpowers task builds on the ones before it. Task `N` is brief `N` of `<id>`: `FORGE brief --superpowers-plan <f> --task N > .forge/work/<id>/brief-N.md`, its ids are `<id>-N`, and it goes through Medium steps 2–6 (baseline, implementer, validators, verify, reviewers, verdict) like any Medium brief. Its implementer commits as the task's last step says.
5. When a task is accepted (`done` in step 6): `FORGE sp-plan check <f> --task N` ticks its boxes and prints `checked`. Commit the plan alone only when `checked` is above 0 and git tracks it (`git ls-files --error-unmatch <f>` succeeds): write the message `<plan title>: task N done` to `.forge/work/<id>/commit-N.txt` with the Write tool (the title never goes in a shell string), then `git commit -F .forge/work/<id>/commit-N.txt -- <f>`. When git does not track it (`docs/superpowers/` is often ignored), the ticks stay on disk only. Then the next task.
6. `breaker` or `stalled` with findings that block the work: stop there, since the later tasks build on this one. Tell the user which task stopped and why; its boxes stay unticked.
7. At the end, Medium step 7: the phase `done` and the report (one line per task with its verdict and commits).

## Large

Subsystem, architecture, much ambiguity or risk, or a greenfield project. Gate: **mandatory approval** of the design.
1. **Design.** Log the phase `design` (and `plan` when step 2 starts, so lens shows where the run is). **From a spec:** with `--from-spec <f>`, run `/waypoint:design new --from <f>` instead of writing the design from scratch. Without it, before writing a design from scratch, run `FORGE sp-specs` (specs superpowers wrote here in the last 14 days that no design imported yet): when it lists any, ask once with AskUserQuestion «¿Parto del spec `<path>` (<title>)?», in the user's language, the newest first plus «No, un diseño nuevo»; on a yes, `/waypoint:design new --from <path>`. Run `/waypoint:design` to write and iterate `docs/waypoint/<project>/design.md` with the critic. Wait until the user approves it (`/waypoint:design approve`). Never approve it yourself. Under forge, `approve` runs only its steps 1–3 (approve, snapshot, publish); its step 4 (`waypoint:plan`) is replaced by step 2 below. That approval also covers the private roadmap publish that `/waypoint:plan` does. Once approved (the project id is known), write `.forge/work/<project>/run.json` with `{ "base": "<git rev-parse HEAD>" }` only if that file does not exist yet; never overwrite it (on resume it keeps the run's original base).
2. **Plan.** Get waypoint's CLI path with `FORGE waypoint-cli`. Spawn `forge-planner` with the design path, the plan path `docs/waypoint/<project>/plan.yaml`, the user's language, that path and the repo root. Show the user the phase outline it replies with and ask once for confirmation (as waypoint's plan step does). If the design's `start_prompt` contains `<track>`, rewrite it in `design.md` yourself: replace `<track>` with the id of the plan's first track and append ` — forge drives this session (forge:run Large loop)`, so the default becomes `/waypoint:work <track id> — forge drives this session (forge:run Large loop)` and parallel sessions launched from it run the forge loop too (`/waypoint:launch` adds the forge suffix to them when the design's `start_prompt` carries it) (small commit, no new design version). Then re-run `design-page` and re-publish to the design's `artifact` URL, as the `waypoint:plan` skill's `start_prompt` paragraph says. Then run `/waypoint:plan`: plan.yaml now exists, so it validates, publishes the live roadmap and syncs it.
3. **Tasks.** **Mode.** Run `FORGE swarm propose --plan <plan>`. Do not ask when the user already said how ("en enjambre", "con sesiones", "con subagentes", "en paralelo", "secuencial"), when `configured` is not null, or when `recommended.parallel` is 1 (then say in one line that it runs one task at a time, and why). Otherwise ask once with AskUserQuestion: the recommended option first, labelled "(Recomendado)", with its `reasons`, then "Enjambre de sesiones" (you can talk to each task's session; useful in very long plans) and "Secuencial". "Enjambre de sesiones" is mode `sessions`: Execution step 1 runs `FORGE swarm start … --mode sessions` and each task runs in its own background session (a run member, below); the other options are mode `subagents`. N is the user's `--parallel` if given, else `recommended.parallel`. Then follow **## Execution** with the chosen mode and N (N = 1 is the sequential path), and come back to step 4 when it finishes.
4. **Final review.** When every task of the run is done (or at a phase close the user asks to review). Validation here includes the e2e and bench validators when the project has them: forge detects them; list them in `.forge/config.yaml` only when detection misses them.
   - `FORGE validate --final --task <project>-final --cwd .claude/worktrees/run > .forge/work/<project>/final-validators.json`.
   - `git -C .claude/worktrees/run diff <base>..HEAD > .forge/work/<project>/final.patch`, with `base` from `.forge/work/<project>/run.json`. The run worktree holds the whole run on `forge/run-<project>`; the final review is of all of it.
   - Spawn `review-correctness` in final review mode with the design path, the plan path and that diff, output dir `.forge/work/<project>/final-1/`. Then `FORGE verdict --task <project>-final --dir .forge/work/<project>/final-1 --validators .forge/work/<project>/final-validators.json` and act on the verdict's `action` (not the reviewer's own `verdict`).
   - If the action is `fix` or `redo` (a whole run is never redone: `redo` is treated as `fix`): one fix by `impl-heavy` with the final review JSON as its brief, the absolute path of the run worktree (it works and commits there, on `forge/run-<project>`), report path `.forge/work/<project>/final-fix.txt`, task id `<project>-final`.    - The final review covers only what is integrated into the run branch. With the verdict, list to the user the task branches not integrated yet (`git branch --list 'task/*' --no-merged forge/run-<project>`): their work was not reviewed.
5. Log the phase `done`, then report: the roadmap URL, tasks done, verdict scores, rulings, task branches not integrated, and the automatic decisions (`## Decisions`, both `--task <project>` and `--run <runId>`).

Every message to the user, also after a Stop-hook block or a wake, is in the user's language (the plan's `locale`). `WP` = `FORGE waypoint-cli`; `DB` = `.waypoint/<project>/dbcache`; `SID` = this session's waypoint id (run `/waypoint:work` §0 Setup once if `.waypoint/<project>/session.json` does not exist, then stop following `/waypoint:work`). This session stays in the main checkout and never cd's anywhere: commands that act in a worktree take `--cwd <worktree>`; files there are read and edited by absolute path.

### Run member

If `join` returns a `warning` (the id was not filled in), go on and tell the user once that this session will not show its own live signal. Session ids follow the members rule (letters, digits, `_ - .`, at most 120): if `join` refuses yours, tell the user and stop. If `<MAIN>/.forge/work/<T>/handover.md` exists (a relaunch wrote it), read it before anything else: it names the last stage, round and the commits already on `task/<T>`. ### Manual member

`/forge:run --join` (also what `/waypoint:work` §0.6 sends here): a session the user drives joins a running execution and works plan tasks next to it. Read `<MAIN>/.forge/execution.json` (as in `### Run member` step 2) for `runId`, `coordinator` and `branch`; `<plan>` is the plan of its `project`.

If your zones overlap a running task, send the coordinator an `overlap_warning` (`/waypoint:work` §6) before you touch them. Then go back to step 2 if the user wants to go on.

### Requests during an execution

While an execution is active the new work lives on the run branch, not in the user's branch. At start (Execution step 1) say in one line: «para ver la app en marcha, ábrela desde `.claude/worktrees/run`». What the user asks in the coordinator session, by its triage (`## 1. Triage`):
- **Trivial or Small, "aplícalo ya"**: do it in the run worktree (`--cwd .claude/worktrees/run`, files by absolute path) with its own commit on the run branch, so it shows at once. If its files overlap a running task, do not step on it: say so and turn it into a new plan task with `depends_on` that task (as Medium below).
- **Medium**: a new plan task (track, `depends_on`, zones, `done_when`), a plan commit and the sync (`/waypoint:plan`); the next `tick` starts it when a slot is free.
- **Large or a new block** (a phase or a version): `/waypoint:design` of the next version and then its plan, without stopping the execution; it picks the new tasks up when the plan is synced.
- **Questions and discussion**: answer them in the session. What must stay (decisions, open questions) goes as a roadmap note, which other sessions read as information, never as an order.

What the user asks in another session follows `### Manual member`, with the same size rules.

### Unattended

An execution is unattended when it runs under `/forge:infinite`, when this session has an active `/goal`, or when this session is a run member. An unattended execution never stops to ask: the only questions are the ones at start (budget, mode, final merge). Any other question becomes a question note on the roadmap (`notes/<EID>` `{ts: NOW, type: "question", author: "session:<SID>", text, taskId?}`) and the run takes the safe path:

| Situation | Safe path |
|---|---|
| A verify surface not allowed, or changed | Not verified in that step: `verify-skip` logged, plus the question note. |
| A Large task | Blocked with the question; the others go on. |
| A conflict that repeats | Escalated; the task stays blocked or in conflict and the others go on. |
| A proposal outside the policy | Left pending for the user. |

Record each such decision as `## Decisions` says: `point: "safe-path"`, `by: "unattended"`, `safePath` the row above, `chosen` what you did instead, `task` the task when there is one, and the `undo` that fits (`none` when nothing was done). It stops only for the usual causes: budget, `.forge/stop`, 3 cycles without progress, the same error twice, a full queue or `/forge:stop`; while unblocked work remains, it goes on. With a `/goal`, the coordinator does not depend on the Stop hook's block to continue (its agents and its background timer wake it), and when it closes it writes the checkable line of Execution step 7.

### Ephemeral execution

Parallelism outside a plan (spec §4.4): the same scheduler and the `subagents` executor, with no waypoint plan, integrated **into the current branch** one task at a time.

**When.** A message with several requests ("haz A, B y C"): split them, write each one's text to `.forge/work/<id>/task.txt` and run `FORGE triage --task <id> --text-file .forge/work/<id>/task.txt --batch` for each. A Large one leaves the batch and follows `## Large` after it. Also a Medium task whose briefs can run in parallel (`## Medium` step 2). If only one task is left after the split and the triage, there is no ephemeral execution: it is a normal task.

**Loose ids.** Loose ids repeat between runs, and a repeated id would inherit the ledger history (triage ratchet, round history) and the stale `.forge/work/<id>/` of an unrelated earlier task. So each loose id is `<slug>-<tag>`: `<slug>` a short kebab-case slug (at most 40 characters) and `<tag>` 4 lowercase base-36 characters derived from the time the run starts, the same for every task of the run: `node -e "console.log((Math.floor(Date.now()/1000)%1679616).toString(36).padStart(4,'0'))"`, run once, before the first `.forge/work/<id>/`. The result is at most 45 characters, so it passes the plan-id rule (`[A-Za-z0-9_.-]`, 64 at most) with room for a Medium brief's `-<n>`. Medium brief ids stay `<id>-<n>`, with `<id>` the Medium task's own id.

1. **Tasks.** With the Write tool, `.forge/work/loose-tasks.json`: `[{id, title, path, zones, depends_on}]`, one per request (or brief); `path` is `trivial`, `small` or `medium`. `zones` are the triage `files` (an empty list means the whole repository, so that task runs alone); `depends_on` lists the requests that need another one first (you judge it from the text: "luego usa eso en B").
2. **Start.** Check the tree as `Rules for every path` says (changes that are not yours → ask first; when you ask, say that "leave them" means no task can be integrated — `integrate` answers `run-dirty` — until they are committed or stashed). `SID` = this session's waypoint id (`sessionId` in `.waypoint/<project>/session.json`) when that file exists, else `loose-<UTC yyyymmddHHMMss>` (also when `start` refuses the waypoint id for its characters). `FORGE swarm start --project loose --session <SID> --kind ephemeral --tasks .forge/work/loose-tasks.json` (code 2 — another execution is active, a leftover worktree or branch of the same id, the checkout not on a branch —: tell the user its message and do the requests one after the other). It takes `parallel` = min(the configured N, how many tasks can run at once) by itself; do not pass `--parallel` unless the user gave one. Mode is always `subagents`; if the user asked for sessions, say in one line that an ephemeral run uses subagents. Tell the user in two lines: the tasks, how many at once (`parallel`), that each lands on `<current branch>` as soon as it is accepted, whether they show on the roadmap as loose tasks (only when the project has one), and that `/forge:stop` ends it. Then publish as `## Execution` step 5 says for an **Ephemeral run.**
3. **Loop.** `## Execution` steps 3, 4, 5 and 6, with these differences: `FORGE swarm tick` takes no `--plan` nor `--db`; there is no step 2; step 4 skips its DB, proposals and `state/T` parts (no listing into `DB`, no `proposals pull`, no `state/T` claim, mirror or `forge` update); step 5 is its **Ephemeral run.** paragraph (with a roadmap: `meta/run` with `kind: "ephemeral"` and `loose`, and your `sessions/<SID>` lease; never `state/T` nor the inbox; without one, nothing is published and lens and the band show the run from the local files). `start {task}`: `FORGE swarm worktree <T>` → `{worktree, branch, base, setup}` (a task worktree off `<current branch>`), with no roadmap claim, then the task's steps. **A task's steps**, per task `T` with its own triage (a Medium brief: the Medium task's):
   - **brief:** write `.forge/work/T/brief-1.md` yourself from its request (or the Medium brief), with the absolute worktree path and "work only inside this directory"; then `FORGE validate --all --path <path> --base-run --task T-1 --cwd <worktree> > .forge/work/T/baseline-1.json`.
   - **implement:** spawn the agent named by the triage's `implementer.agent` for `T`, as printed, in the background (for a Trivial of a batch it is the `mech` role's agent, from `--batch`), as `## Execution` step 4.2 says.
   - **validate:** as step 4.3, with `--path <path>`.
   - **Trivial and Small:** no reviewers. Read `git -C <worktree> diff <base>..HEAD` yourself: right → `FORGE swarm task <T> --stage verdict --status accepted --no-agent`; wrong → resume the implementer with what you found and validate again (after two such rounds, a fresh implementer one tier up; after that, `FORGE swarm task <T> --status blocked --detail-file <f>`).
   - **Medium:** verify, review and verdict as steps 4.4 and 4.5, with `--path medium`. Reviewers: `review-correctness` always; `review-security` only when the triage found a sensitive zone (and then `--sensitive` on the verdict); `review-perf` only for performance tasks (and then `--perf`).
   - **integrate:** `FORGE swarm integrate <T>` merges `task/<T>` into `<current branch>` in the main checkout. `integrated` → no roadmap write; when its `preexisting` is not empty, tell the user in one line which validators were excused as already failing on `<current branch>`. `conflict` → `FORGE swarm retry <T>` once. Then `BASE=$(git rev-parse <current branch>)`, `git -C <worktree> checkout --detach $BASE`, `FORGE validate --all --path <path> --base-run --task T-1 --cwd <worktree> > .forge/work/T/baseline-1.json`, `git -C <worktree> checkout task/<T>`; `<base>` = `$BASE`. The implementer merges `$BASE` (the sha, not the branch name) into `task/<T>`, so `<base>..HEAD` holds only this task's work: name that sha in its brief, with the conflict detail. If something was integrated meanwhile, the next `integrate` may conflict again; that is the second-conflict path: tell the user and leave it in conflict. `run-dirty` → your checkout has uncommitted changes: tell the user once that no task can be integrated until they are committed or stashed, and keep stepping. Code 2 because the main checkout is on another branch: tell the user to switch back to `<current branch>`, and keep stepping.
4. **End.** On `finish`: no final review and no `swarm merge`. Report one line per task (what changed, its implementer, its verdict or "read the diff") and the checkable line «Ejecución <runId> terminada: N/N tareas integradas en <current branch>». Then the automatic decisions of the run (`## Decisions`, `--run <runId>`). On `stalled`: its reason per task. In both, with a roadmap: publish `meta/run` once more with `active: false` and `sessions/<SID>` `{status: "idle"}` (`## Execution` step 5, **Ephemeral run.**).

**Resume.** When `FORGE swarm status` shows an active `kind: "ephemeral"` run that you coordinate: `FORGE swarm start --project loose --session <its coordinator> --kind ephemeral` (no `--tasks`: the run keeps its own), reconcile each task in `running` as `## Resuming` step 4 says for a subagents task (stage, agent, round and worktree from `FORGE swarm status`; an agent no longer running is respawned for that step; a verdict already written is not recomputed), then step 3.

## Resuming

1. `FORGE last --task <id>`: `path` and `phase` (the whole last phase event, with its `brief` number `n`).
2. `FORGE last --task <id>-<n>`: the last verdict (with its review `dir`) and the last round of that brief.
3. Continue from there; the phase event's `base` is the `BASE` for `redo`; never redo finished work. If the last verdict already covers the newest review dir, do not run `FORGE verdict` on that dir again: go on with `FORGE round` (or the `next` of the last round). Run a verdict only for a review dir that has none yet.
4. In an execution (`FORGE swarm status` shows it active and you are its coordinator; the SessionStart context says "Resume it with /forge:run → Resume", or you came back with `claude --resume`): renew your lease, then run `FORGE swarm start` with the same `--project` and `--session`, plus the `--mode` and `--parallel` that `FORGE swarm status` shows (and `--kind ephemeral` for an ephemeral run, which then follows `### Ephemeral execution` → Resume) (it resumes without changing anything; without them `start` takes the mode and N from `.forge/config.yaml`). Reconcile each task in `running`: a subagents task as before, reading its stage, agent, round and worktree from `FORGE swarm status` and its review dirs (`.forge/work/<T>/reviews-*`): an agent that is not running any more is respawned for that step; a verdict already written is not recomputed. A sessions task by ListAgents: a live `wp-<project>-<T>` session is left alone; a dead one gets the `relaunch` action of the next `tick`. Then go to Execution step 2.
   **Takeover.** A new session asked to go on with the execution ("sigue con la ejecución") while another session coordinates it: get `SID` (`/waypoint:work` §0 Setup items 1–4), list `sessions` into `DB` (Execution step 2), then `FORGE swarm takeover --session <SID> --db DB`. `took: true` → register as coordinator (`sessions/<SID>` as Execution step 1, with its lease; the Stop hook binds to this session at its next stop or agent start), claim again with a versioned write the `owner` of each task it lists as `running` whose `executor` (`FORGE swarm status`) is `subagents` (`update state/T` `{owner: SID, exec: {by: SID}}` pinned to its version), publish `meta/run` (Execution step 5) and go on from step 4 above. `took: "already"` → you already coordinate it: step 4 above. `took: false` → tell the user who coordinates it (`previous`, and its `liveness`) and join as a manual member (`/waypoint:work`, which sends you to `### Manual member`).
