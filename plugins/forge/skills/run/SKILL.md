---
name: run
description: Do a software task with the forge method - triage by size, the right model per step, tool-first validation and weighted independent review; on the Large path it coordinates an execution that drives each task through subagents or background sessions on a run branch (--parallel N, default 3). Several independent requests in one message, and the independent briefs of a Medium task, run in parallel as an ephemeral execution integrated into the current branch. Use for any coding task the user asks to "forge", or via /forge:run <task> [--parallel N]; `--from-spec <spec>` starts the Large path from a superpowers spec, `--superpowers-plan <plan>` runs a superpowers plan task by task; `--auto` (or `autonomy: auto`) asks only at launch and records every decision it takes; a session launched for one task of an execution runs it with forge:member, and /forge:run --join joins a running execution as a manual member.

# forge: run a task

`FORGE` below means `node "${CLAUDE_PLUGIN_ROOT}/dist/forge.cjs"`. Work files go in `.forge/work/<task-id>/` (task id: a short kebab-case slug of the task, or the waypoint task id when one is in progress). Keep internal names in English.

**Language.** Every message to the person is in the language they write in, not that of this skill, a CLI output or an agent's reply. That holds right after a Stop-hook block, a wake or an agent's return too: those texts are English for you, never for them. Between tool calls write nothing, or one short line in their language; never paraphrase a step of this skill («Now mirror the stage…»).

Ids: `<id>` is the task id, used for triage and phase logs. Each brief of a Medium or Large task gets its own id `<id>-<n>`, used for `review-prep` and `review-close` (round counting is per brief) and as the task id you hand to the implementer; for Large, `<id>` is the plan task id. Before spawning agents, resolve `${CLAUDE_PLUGIN_ROOT}` to an absolute path and give subagents the absolute path of `forge.cjs`, never the variable.

Never put user text or JSON inside a shell string. Write the task text to `.forge/work/<id>/task.txt` and any log data to a JSON file (e.g. `.forge/work/<id>/log.json`), then pass the file flags (`--text-file`, `--data-file`).

Rules for every path:
- Irreversible or outward actions (delete, merge into main, publish) always need the user's approval; never push without being asked.
- Before you start, run `git status --porcelain`. If the tree has changes that are not part of this task (the user's own work, an earlier task left uncommitted), ask the user whether to commit, stash or leave them before you go on; never commit, stash or discard them on your own. forge's work files (those `.forge/.gitignore` ignores) do not count; `.forge/config.yaml` and `.forge/verify/*.md` are the person's. Then `FORGE tree snapshot --task <id>` (with `--cwd <worktree>` for a task in a worktree).
- Never delete, revert, move or overwrite a file this task did not create. The task created only what its commits hold and its files under `.forge/work/<id>/`. Before closing a task (its report, a commit of surface notes, anything that tidies the tree), run `FORGE tree check --task <id> --base <BASE>` (with the same `--cwd` as its snapshot): every path in `appeared` or `changed` is the person's, also an uncommitted edit to a file the task committed (a `snapshot: null` or a `warning` means the snapshot could not be trusted: treat every untracked and modified path that way), whenever it appeared and whatever it holds; never guess that an agent made it (agents do not write project files). Ask commit/stash/leave as above, and leave it by default.
- Always name the agent when you spawn one (subagent type `forge:<agent>`); never let work inherit your own model. Roles (`impl`, `review-security`, ...) map to agent names through `FORGE agents` (it applies the profile in `.forge/config.yaml`).
- The implementer **tier ladder**, in roles: `mech` -> `impl-light` -> `impl` -> `impl-high` -> `impl-heavy`. The first attempt takes the implementer triage prints (`impl-high` for a sensitive Medium or a sensitive plan task), or `impl-high` for a plan task the design marks delicate; every fix round takes the implementer `FORGE review-close` prints (`implementer.agent`: the same one on `resume`, one rung up on `fresh-stronger` or a redo with `tierUp`, `impl-heavy` on the attempt it marks `last`). Spawn that agent as printed and never compute the ladder by hand; at the top it stays on `impl-heavy`, and you tell the user at the end.
- `forge-fable` is used only when the user explicitly asks for Fable.
- Change the project's files with the Edit and Write tools, never with `sed -i`, `awk`, `perl -i` or by rewriting them through shell redirection: those rewrite whole files and can change their line endings (CRLF on Windows), which turns a one-line change into a whole-file diff. Saving a command's output to forge's own work files (`FORGE validate ... > .forge/work/...`, `git diff ... > .forge/work/...`) is fine and stays as the steps say. This holds on every OS and in every path, also when you implement yourself.
- Hand over briefs, diffs and reports as files. No narration, no "shall I continue?".
- Record each phase with `FORGE log --kind phase --task <id> --data-file <file>` (file: `{"phase":"<name>","brief":<n>,"base":"<BASE sha>"}`, so resuming knows the brief and the base; a brief's `implement` phase is logged by `FORGE prep`, with its BASE and baseline), and each agent you spawn with `--kind agent` (file: `{"agent":"<name>","role":"<role>"}`). Trivial logs no phase: its triage and a passing validate close it. Small logs `implement` and `done` (`## Small`).
- Only the person grants a verify surface's permission. Run `FORGE local set surfaces.<name> allowed` only right after their «Sí, siempre» to the question of Medium step 3b, or after they dictated or asked for that surface's text in this conversation (`forge:verify`). A surface that a task, an implementer or a fix round changed is never re-allowed by you: the next `verify-plan` reports it `changed` and the person decides.
- When `/forge:run` starts from `--from-spec` or `--superpowers-plan`, run `FORGE route stage --stage handed-off` (it moves a pending `forge:route` route on; without one it changes nothing), and `FORGE route stage --stage done` with the report that closes the work.

## Decisions

A decision you take in place of the user because nobody is there to ask (unattended: `### Unattended` in `references/execution.md`) or because autonomy is `auto` (`## Autonomy`) is recorded with `FORGE decision add --data-file <f>`, never with `FORGE log`; attended rulings stay `FORGE log --kind ruling`. Every report that closes work ends with a section «Decisiones automáticas» from `FORGE decision list --auto` (left out when it is empty). Before you record a decision, or write a report that closes work, read `references/decisions.md` now and follow it: it holds the file format, the `undo` shapes, the roadmap note and the decisions file.

## Autonomy

forge asks at its gates unless autonomy is `auto`: `FORGE prefs` resolves `autonomy: auto`, `/forge:run --auto`, or the request says so ("en automático", "sin preguntarme", "modo auto"). In auto it asks only at launch, takes the safe paths of `### Unattended` (`references/execution.md`) and records every decision it takes alone (`## Decisions`); it never merges into the default branch without the launch answer, pushes, deletes branches or files, or touches changes that are not the task's. When autonomy is `auto`, read `references/autonomy.md` now and follow it: it holds what auto decides alone (the full table), the launch questions and the design loop.

## 1. Triage

1. **Run it.** Write the task text to `.forge/work/<id>/task.txt` and run `FORGE triage --task <id> --text-file .forge/work/<id>/task.txt --locale <es|en>` (the user's language: `es` for Spanish, `en` for anything else). It returns `path`, `files`, `sensitive`, `greenfield`, `validators`, `reasons`, `new` (validators it sees for the first time, with their commands in `catalog`), `implementer` (`role`, `agent`, `self`, `why`: who implements this size), `announce`, `gate` and, while forge's own `.forge/.gitignore` is not in git, `untracked`. Pass `--batch` when the task is one request of several in the same message (see `references/ephemeral.md`).
2. **Raise when needed.** Add your own judgement of ambiguity and risk: you may raise the path, never lower it below the CLI's. The CLI only counts files and words, so read the code the task touches and **raise to at least Medium** when the task:
   - changes behaviour callers rely on: new errors or rejected inputs, a changed signature, different return values;
   - bundles several independent changes;
   - adds new behaviour with its tests, rather than a mechanical or one-spot fix.
   To raise, log it with `FORGE log --kind triage --task <id> --data-file <file>` (file: `{"path":"<new path>","why":"<the reason in the user's language, e.g. cambia el contrato de addItem>"}`) and run step 1's command again: it keeps the highest path logged and its `announce` now names your reason. This is the **ratchet**: the path only goes up, also later in the task (e.g. small -> medium when the change turns out to touch a sensitive zone; log it the same way), and you follow the raised path from then on.
3. **Announce.** Print `announce` exactly as printed, as the first lines of your reply, before any brief, edit or spawn, also late in a long session. It names the path, the reason, the implementer and any new validator with its command, and says the user can correct it; do not ask anything. When you do a Small yourself (the exception in `## Small`), add «lo hago yo, el cambio ya está en contexto».
4. **forge's own files.** With `untracked` (`.forge/.gitignore`, which keeps forge's work files out of git), commit it alone right away: `git add .forge/.gitignore` and `git commit -m "forge: track .forge/.gitignore" -- .forge/.gitignore`. It is forge's file, not one of the user's changes.

A run member (forge:member) runs in the background: it prints nothing of this, and the coordinator announces new validators when it integrates.

**TDD.** Run `FORGE tdd` once per task. When its `line` is not null, every implementer brief you write by hand (Small, Medium, ephemeral and execution briefs) ends with that line as printed (it starts `TDD: required`; `FORGE brief` adds it itself), and when you spawn `review-correctness` for such a brief you also give it the implementer's report path. When `tdd` is `superpowers` and `line` is null, say in the triage line that superpowers is not installed (or has no `test-driven-development` skill) and that the task goes on without TDD.

**From a spec.** With `--from-spec <f>`, with or without task text, write the spec's title and the first paragraph of its purpose section to `.forge/work/<id>/task.txt` (`<id>` from the spec's file name, as `waypoint:design new --from` derives the project). The path is Large whatever `FORGE triage` prints: log the raise as the ratchet says (`{"path":"large"}`).

If the user, at any point, explains how to check something of the project ("para probar X usa Y"), follow the `forge:verify` skill: write or update `.forge/verify/<name>.md` without asking.

If a waypoint task is in progress (the waypoint work skill claimed it), use its id as the task id.

## Trivial

One file, obvious change. No gate.
1. Implement it yourself.
2. `FORGE validate --affected <file> --task <id>`; fix until it passes (stop after 3 tries and report). A passing validate closes the task for lens and the roadmap.
3. Report in two lines: what changed, validation result.

## Small

<= 3 files, no ambiguity, no sensitive zone. No gate, no reviewers.
0. Record `BASE=$(git rev-parse HEAD)` and log the phase `implement` (`{"phase":"implement","brief":1,"base":"<BASE>"}`).
1. A Small task is **always delegated**: write `.forge/work/<id>/brief-1.md` (what to change, the files, the exact values) and spawn the agent that the triage output's `implementer.agent` names, as printed (the `mech` role for mechanical work — renames, data, code already written —, the `impl-light` role otherwise; the profile picks the agent) with the brief, the report path `.forge/work/<id>/report-1.txt` and the absolute FORGE path; log it with `--kind agent`. The only exception: the whole change is already in your context (you read it in this turn) and it is 10 lines or fewer. Then do it yourself and say so in the triage line ("Small: lo hago yo, el cambio ya está en contexto").
2. `FORGE validate --all --path small --task <id>`.
3. Read the real `git diff $BASE` yourself and fix what you find.
4. **Verification, only when the task asks for it** (check it in a browser, an emulator, a device): `FORGE verify-plan --task <id> --path small --base $BASE --asked --locale <es|en>` and handle its surfaces as Medium step 3b says (drafts, the permission questions, which surfaces and how deep). To verify, spawn `verify` with the brief, `git diff $BASE`, the chosen surfaces, the depth, the `missing` and `unknown` tools, review dir `.forge/work/<id>/reviews-1-1/` and evidence dir `.forge/work/<id>/evidence/1-1/`, and log it with `--kind agent`. When it returns: `FORGE verify-result --task <id> --dir .forge/work/<id>/reviews-1-1` (it records the result, so lens does not show the task running), then its learned notes and `verify-cleanup` as after a Medium verdict (step 6). A failed check goes back to the implementer like a problem in the diff.
5. Log the phase `done` (`{"phase":"done","brief":1,"base":"<BASE>"}`), then report in two lines.

## Medium

Several files or some design; moderate risk.
0. **Gate.** When the triage's `gate` is `plan`, print the short plan (at most 10 lines, one per brief: `N. <brief> — <files> — <validators>`) right after `announce` and before any brief is written or any agent spawned, then **continue** unless the user stops you. Never skip it, also late in a long session.
1. If `validators` is empty, the first task creates minimal tests for what you will touch.
2. For each task, write `.forge/work/<id>/brief-<n>.md` (requirements, exact values, files) and, before any change, run `FORGE prep --task <id>-<n> --path medium` (once per brief; fix rounds reuse what it wrote; on the Large path use `--path large`): in one call it reads BASE (HEAD; the `base` it prints is the `$BASE` of the steps below), records what already fails on BASE into `.forge/work/<id>/baseline-<n>.json` (as `FORGE validate --all` on BASE would) and logs the phase `implement` with the brief number and BASE. A failure that BASE already had (a build that needs a file a later task creates) is not this brief's fault and does not count. Spawn the triage's `implementer.agent` as printed (`impl`, or `impl-high` on a sensitive zone), or `impl-high` for delicate or important work (logged with its role, `--kind agent`, as every implementer), with the brief, a report path `.forge/work/<id>/report-<n>.txt`, the task id `<id>-<n>` and the absolute `FORGE` command. If the implementer could not write the report file, save the report from its reply (after `--- report ---`) to that path yourself. **Briefs in parallel.** When the short plan has two or more briefs and at least two of them neither depend on each other nor share a file, run the briefs as an ephemeral execution (`references/ephemeral.md`, one loose task per brief: id `<id>-<n>`, path `medium`, zones the brief's files, `depends_on` the briefs it needs) instead of one after the other. A brief that depends on another starts once that one is integrated. Each brief's work files are then in `.forge/work/<id>-<n>/` (its loose task's directory: `brief-1.md`, baseline, validators, reviews). When that execution ends, go on with step 7 below.
3. Instead of validating and writing the diff yourself, run `FORGE review-prep --task <id>-<n> --path medium --base $BASE --baseline .forge/work/<id>/baseline-<n>.json --dir .forge/work/<id> --locale <es|en>` (on the Large path `--path large`) and print its `say` as it is. It validates against the baseline into `.forge/work/<id>/validators-<n>.json` (a failure BASE already had is marked `preexisting: true` and the verdict leaves it out; a test runner that finds no tests passes as `skipped: "no-tests"`), writes `.forge/work/<id>/diff-<n>.patch` and, from round 2, the fix diff `fix-<n>-<round>.patch` and each reviewer's own previous findings; it decides who reviews from the triage's `review` and prints `round` (this review's round), `validators`, `spawn` (one entry per agent to launch: `agent`, `model`, `effort`, `mode` `full` or `delta`, `inputs`, and `twin: true` for a shadow twin) and `carried` (reviewers whose previous result is copied to this round, not spawned).
3b. **Tool verification.** `FORGE verify-plan --task <id>-<n> --path medium --base $BASE --locale <es|en>` (add `--asked` when the task text asks to check it in a browser, emulator or device).
   - For each `drafts` entry: propose the draft (`FORGE surfaces` shows its body) once; with a yes, write `.forge/verify/<name>.md` keeping the draft's `affects` and `tools` header from `FORGE surfaces` as it is (the body in the user's language) and `FORGE local set surfaces.<name> allowed`; with a no, `FORGE surfaces proposed --name <name>`. Then run `verify-plan` again. Commit the new surface with the task's work (plus `.forge/.gitignore` when git does not track it yet).
   - For each surface with `permission: changed`: its file changed since the user allowed it (someone edited the instructions: a commit, a PR, a task). Show the change itself, never a summary: its `commits`, then its `diff` verbatim in a ```diff block (when `diff` is null: `git log -p -n 3 -- .forge/verify/<name>.md`). When `diffTruncated` is true, show the rest from `diffFile` too: never offer «Sí, siempre» on a change the user has not seen whole (with `diffTruncated` and no `diffFile`, ask with only the other two options). Then ask with AskUserQuestion: `ask.question` with exactly the three `ask.options`, in that order. «Sí, siempre» → `FORGE local set surfaces.<name> allowed --expect <the surface's hash from verify-plan>` (it stores the new content's hash, and refuses when the file changed after the question: then run `verify-plan` and ask again); «Nunca en este proyecto» → `denied`; «No, esta vez» writes nothing. After the answer run `verify-plan` again.
   - For each surface with `permission: ask`: ask once the same way, with its `ask` (it names the surface, its title and its tools), and allow it with `--expect` as above. Then run `verify-plan` again.
   - Nobody to ask (`### Unattended` in `references/execution.md`, also auto mode): do not ask and do not allow anything; take that table's safe path (not verified, a `verify-skip` and a question note).
   - With `eligible: true`, decide per surface whether it is worth it and the depth (`smoke` or `flow`). A surface without `affects` (`match: null`) is verified only if the diff and its description are related. For each candidate you skip: `FORGE log --kind verify-skip --task <id>-<n> --data-file <f>` (`{"surface":"<name>","reason":"<one line>"}`). This also holds when you skip every surface of an eligible plan: log one `verify-skip` per surface, so the ledger records why nothing was verified.
   - If you verify: spawn `verify` (resolved with `FORGE agents`) **in parallel with the reviewers in step 4**, with the brief, the diff, the chosen surface files, the depth, the `missing` and `unknown` tools (`unknown` ones may be MCP servers forge cannot see in the configuration: the agent tries them), review dir `.forge/work/<id>/reviews-<n>-<round>/` and evidence dir `.forge/work/<id>/evidence/<n>-<round>/` (`<round>` the `round` review-prep printed in step 3), the limits from `.forge/config.yaml`, the absolute FORGE path and, in a fix round, the previous `verify.json` of this brief. Never pass it a reviewer's output, nor its output to a reviewer.
4. Spawn exactly the entries of review-prep's `spawn`, nothing more and never a `carried` one: each as its `agent`, with its `mode` (`full` or `delta`) and its `inputs` (`brief`, `diff`, `validators` and `out`, the review dir `.forge/work/<id>/reviews-<n>-<round>/`; with `mode: delta` also `fix`, the fix diff, and `findings`, that reviewer's own previous findings; `report`, for correctness under `TDD: required`, the implementer's report), passing the Agent tool's `model` when the entry's `model` is not null and the Agent tool's `effort` always. A `twin: true` entry (round 1 while the shadow test is open) is spawned the same way, with its own `out`: the `shadow/` folder of the review dir; it never counts in the verdict. They run independently: spawn them in parallel and never pass one reviewer's output to another. Reviewers set `"approach": "wrong"` in their JSON when the change should be redone with another approach rather than patched.
5. Each time you are told a reviewer finished, not only when the last one does, check that it wrote its file in its `out` (`correctness.json`, `security.json`, `perf.json`, and `verify.json` in the review dir when `forge-verify` was spawned): a reviewer that finished without its file is respawned at once with the same entry, and you never end the turn while a spawned reviewer has neither its file nor a running agent (nothing would wake you). Go to step 6 only once every spawned entry has returned, twins included: review-close compares only the twins whose file is there when it runs, so a twin that finishes later is lost.
6. `FORGE review-close --task <id>-<n> --dir .forge/work/<id> --path medium` (on the Large path `--path large`). It replaces the separate verdict and round calls: it runs the verdict with the triage's flags (`--sensitive`, `--perf`) and the round, decides the round, logs the minor and `deferred` findings as a ruling and prints `{action, score, next, last, implementer, findings, deferred, invalid}`. Exit 3 with `missing` (the files of spawned reviewers that are not there): respawn each of those reviewers at once with its `spawn` entry and run review-close again when they return. If `invalid` names a reviewer (its JSON came out with `invalid: true`), respawn it once with the same entry and the same dir and run review-close again before trusting it (closing the same round again counts once). An invalid review whose JSON was unusable abstained; when only some findings were dropped, the review keeps its verdict and still scores. If it is still invalid after the respawn, keep the result as it is; when findings were dropped, read the reviewer's raw JSON file and record the dropped findings as a ruling (`FORGE log --kind ruling --task <id>-<n> --data-file <file>`, file: `{"dropped":[...]}`). Then follow `next`; the implementer of a fix round is always the implementer `FORGE review-close` prints (`implementer.agent`), never one you work out from the ladder. **Findings to send** below means the file review-close prints in `findings` (`findings-<n>-<round>.json`): the critical and important findings, `deferred` ones left out, plus the `failures` of every validator with `ok: false` and no `preexisting` in `validators-<n>.json`. `deferred` lists the important findings in code the fix did not touch that were the only thing left open: the task goes on, and they go to the final report (step 7) for the person to decide.
   - `done`: next task.
   - `resume`: send the findings to the same implementer (resume it), then repeat from step 3.
   - `fresh-stronger`: spawn a fresh implementer, the one review-close printed, with the brief, the report and the findings to send, then repeat from step 3.
   - `redo`: undo the attempt without rewriting history: `git revert --no-edit $BASE..HEAD` (skip it when HEAD is still `BASE`), then a fresh implementer, the one review-close printed, starts again from the brief with a different approach; repeat from step 3.
   - `breaker` or `stalled`: stop the loop. If what is open blocks the work, tell the user and ask; otherwise record the open findings as a ruling (`FORGE log --kind ruling --data-file <file>`) and continue, telling the user at the end.
   - `tierUp: true` (from round 3) and `fresh-stronger` mean the same single step up the ladder, not two, and `last: true` means the attempt goes to `impl-heavy`: review-close already applies both in the `implementer` it prints, so spawn that one.
   After the verdict, when `verify.json` exists:
   - Append its `learned` notes per surface: write a JSON array of the `note` strings for that surface to a file and run `FORGE surfaces learn --name <surface> --notes-file <f> --heading Aprendido` (or `Learned` in English); never add Learned notes with Edit: `surfaces learn` records each line it adds, so those lines never ask for the permission again (also when parallel tasks add notes to their own copies), while a line added any other way does. If the returned `count` is over 20, propose to the user to summarise that section. The appended surface file is part of the task's changes: commit it with the task's work (or in the phase-close commit), so the tree is not left dirty.
   - Show its `proposals` to the user; apply a proposal to the surface file with Edit only after their yes, and then run `FORGE local set surfaces.<name> allowed` again (their yes covers that text). Unattended, leave the proposals in a question note.
   - Run `FORGE verify-cleanup --dir .forge/work/<id>/evidence/<n>-<round>/` (it stops the processes the agent left running; it deletes no files, and neither do you).
   - **Evidence on the roadmap.** Right before uploading, run `FORGE config get evidence` (the person may have changed it while the task ran; never reuse a value read earlier). When the task has a roadmap (`state/T`) and it prints `upload`: convert any screenshot over 2 MB to JPEG, upload the screenshots of this pass with the Artifact tool (`url: <roadmap url>`, `asset: true`, `file_paths: [...]`, up to 25 per call), then ArtifactData `update state/T` pinned to its version with `evidence: {surfaces, result, passed, total, local: "<evidence dir>", shots: [{url, id, surface, check, ok, expected, observed}]}`. Delete from the roadmap's assets the ids of the previous pass of this task. If the upload fails, write `evidence` without `url`/`id` and with `pending: true`, and retry on the next update of the task. With `evidence: local` or no roadmap, write `evidence` without `url`/`id`.
   A fail of `verify` is a finding like any other: its failed checks are in the verdict's critical/important lists and go in **Findings to send**.
7. Log the phase `done` (same file shape, with the last brief number), so the roadmap and lens show the run as finished. Then report: tasks, commits, verdict scores, rulings, the `deferred` findings review-close printed (one line per finding with its file and line, for the person to decide) and the automatic decisions (`## Decisions`).

### Superpowers plan

With `/forge:run --superpowers-plan <f>` (a plan `superpowers:writing-plans` wrote, run by forge on the Medium path above), read `references/superpowers-plan.md` now and follow it.

## Large

Subsystem, architecture, much ambiguity or risk, or a greenfield project. Read `references/large.md` now and follow it: design (with its mandatory approval), plan, the execution of the tasks and the final review.

## Execution

This session coordinates the execution of a plan's tasks (`references/large.md` step 3, mode `subagents` or `sessions`, N at once, on the run branch `forge/run-<project>`). Read `references/execution.md` now and follow it: start, the tick loop, integration, publishing, the end, requests during an execution and `### Unattended`. A task's steps are in `references/task-steps.md`.

**Run members.** A session launched for one task of the execution (mode `sessions`) runs it with forge:member. Compatibility: a session whose initial prompt is the older `/forge:run --plan <plan> --task <T> — run member of <SID>: work only <T>, then stop` invokes and follows `forge:member` instead of this skill, as does a SessionStart that says "Resume it with /forge:run → Run member".

### Manual member

With `/forge:run --join` (also what `/waypoint:work` §0.6 sends here: a session the user drives joins a running execution and works plan tasks next to it), read `references/manual-member.md` now and follow it.

### Unattended

An execution is unattended under `/forge:infinite`, with an active `/goal`, or in a run member: it never stops to ask after the start. Read `### Unattended` in `references/execution.md` now and follow its safe paths.

### Ephemeral execution

Several independent requests in one message, or the briefs of a Medium task that can run in parallel (Medium step 2): read `references/ephemeral.md` now and follow it. It runs them with the execution's scheduler and `subagents`, with no waypoint plan, integrated into the current branch one task at a time.

## Resuming

To resume a task or an execution (`FORGE last`, `FORGE swarm status`; the SessionStart context says "Resume it with /forge:run → Resume", or `claude --resume`; also «sigue con la ejecución», a takeover), read `references/resuming.md` now and follow it.
