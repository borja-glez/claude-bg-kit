# forge: run a task

`FORGE` below means `node "${CLAUDE_PLUGIN_ROOT}/dist/forge.cjs"`. Work files go in `.forge/work/<task-id>/` (task id: a short kebab-case slug of the task, or the waypoint task id when one is in progress). Speak to the user in their language; keep internal names in English.

Ids: `<id>` is the task id, used for triage and phase logs. Each brief of a Medium or Large task gets its own id `<id>-<n>`, used for `validate`, `verdict` and `round` (round counting is per brief) and as the task id you hand to the implementer; for Large, `<id>` is the plan task id. Before spawning agents, resolve `${CLAUDE_PLUGIN_ROOT}` to an absolute path and give subagents the absolute path of `forge.cjs`, never the variable.

Never put user text or JSON inside a shell string. Write the task text to `.forge/work/<id>/task.txt` and any log data to a JSON file (e.g. `.forge/work/<id>/log.json`), then pass the file flags (`--text-file`, `--data-file`).

Rules for every path:
- Irreversible or outward actions (delete, merge into main, publish) always need the user's approval; never push without being asked.
- Before you start, run `git status --porcelain`. If the tree has changes that are not part of this task (the user's own work, an earlier task left uncommitted), ask the user whether to commit, stash or leave them before you go on; never commit, stash or discard them on your own. forge's own files under `.forge/` do not count.
- Always name the agent when you spawn one (subagent type `forge:<agent>`); never let work inherit your own model. Roles (`impl`, `review-security`, ...) map to agent names through `FORGE agents` (it applies the profile in `.forge/config.yaml`).
- The implementer **tier ladder**, in roles: `mech` -> `impl-light` -> `impl` -> `impl-heavy`. "One tier up" is the next role on it, resolved to an agent with `FORGE agents`; above `impl-heavy` stay on `impl-heavy` and tell the user at the end.
- `forge-fable` is used only when the user explicitly asks for Fable.
- Change the project's files with the Edit and Write tools, never with `sed -i`, `awk`, `perl -i` or by rewriting them through shell redirection: those rewrite whole files and can change their line endings (CRLF on Windows), which turns a one-line change into a whole-file diff. Saving a command's output to forge's own work files (`FORGE validate ... > .forge/work/...`, `git diff ... > .forge/work/...`) is fine and stays as the steps say. This holds on every OS and in every path, also when you implement yourself.
- Hand over briefs, diffs and reports as files. No narration, no "shall I continue?".
- Record each phase with `FORGE log --kind phase --task <id> --data-file <file>` (file: `{"phase":"<name>","brief":<n>,"base":"<BASE sha>"}`, so resuming knows the brief and the base), and each agent you spawn with `--kind agent` (file: `{"agent":"<name>","role":"<role>"}`). Trivial skips this logging: triage and validate are enough.

## 1. Triage

Write the task text to `.forge/work/<id>/task.txt` and run `FORGE triage --task <id> --text-file .forge/work/<id>/task.txt`. It returns `path`, `files`, `sensitive`, `greenfield`, `validators`, `reasons`. Add your own judgement of ambiguity and risk: you may raise the path, never lower it below the CLI's. The CLI only counts files and words, so read the code the task touches and **raise to at least Medium** (log it as below) when the task:
- changes behaviour callers rely on: new errors or rejected inputs, a changed signature, different return values;
- bundles several independent changes;
- adds new behaviour with its tests, rather than a mechanical or one-spot fix.

Announce in one line: path, why (name the reason when you raised it, e.g. "Medium: changes the contract of addItem"), and that the user can correct it. The **ratchet**: during the task the path can only go up (e.g. small -> medium when the change turns out to touch a sensitive zone); log the change with `FORGE log --kind triage --task <id> --data-file <file>` (file: `{"path":"<new path>"}`). Once you raise the path, follow that path: re-running `FORGE triage` for the same task keeps the highest path already logged, and you never go back to a lower one.

If the triage output's `new` list (validator names) is not empty, announce each one in the same message with its `cmd` from the output's `catalog` ("new validator e2e: `npx playwright test`"); do not ask anything.

If the user, at any point, explains how to check something of the project ("para probar X usa Y"), follow the `forge:verify` skill: write or update `.forge/verify/<name>.md` without asking.

If a waypoint task is in progress (the waypoint work skill claimed it), use its id as the task id.

## Trivial

One file, obvious change. No gate.
1. Implement it yourself.
2. `FORGE validate --affected <file> --task <id>`; fix until it passes (stop after 3 tries and report).
3. Report in two lines: what changed, validation result.

## Small

<= 3 files, no ambiguity, no sensitive zone. No gate, no reviewers.
0. Record `BASE=$(git rev-parse HEAD)`.
1. Implement yourself, or spawn the `impl-light` agent (bounded changes) or the `mech` agent (mechanical work) with a brief file.
2. `FORGE validate --all --path small --task <id>`.
3. Read the real `git diff $BASE` yourself and fix what you find.
4. Report in two lines.

## Medium

Several files or some design; moderate risk. Gate: show a short plan (<= 10 lines: tasks, files, validators) and **continue** unless the user stops you.
1. If `validators` is empty, the first task creates minimal tests for what you will touch.
2. For each task, write `.forge/work/<id>/brief-<n>.md` (requirements, exact values, files) and record `BASE=$(git rev-parse HEAD)`. Spawn the `impl` agent (or `impl-heavy` for delicate or important work) with the brief, a report path `.forge/work/<id>/report-<n>.txt`, the task id `<id>-<n>` and the absolute `FORGE` command. If the implementer could not write the report file, save the report from its reply (after `--- report ---`) to that path yourself.
3. Run `FORGE validate --all --path medium --base $BASE --task <id>-<n> > .forge/work/<id>/validators-<n>.json`.
3b. **Tool verification.** `FORGE verify-plan --task <id>-<n> --path medium --base $BASE` (add `--asked` when the task text asks to check it in a browser, emulator or device).
   - For each `drafts` entry: propose the draft (`FORGE surfaces` shows its body) once; with a yes, write `.forge/verify/<name>.md` keeping the draft's `affects` and `tools` header from `FORGE surfaces` as it is (the body in the user's language) and `FORGE local set surfaces.<name> allowed`; with a no, `FORGE surfaces proposed --name <name>`. Then run `verify-plan` again.
   - For each surface with `permission: changed`: its file changed since the user allowed it (someone edited the instructions, e.g. in a commit or a PR). Show what changed, summarised: `git diff -- .forge/verify/<name>.md` (uncommitted changes) and `git log -p -n 3 -- .forge/verify/<name>.md` (committed ones). Then ask "¿Verifico <name> con estas instrucciones? sí, siempre / no, esta vez / nunca en este proyecto": "sí, siempre" → `FORGE local set surfaces.<name> allowed` (it stores the new content's hash); "nunca" → `denied`; "no, esta vez" writes nothing. After the answer run `verify-plan` again.
   - For each surface with `permission: ask`: ask once — "¿Verifico <name> (<its title>, con <tools>)? sí, siempre / no, esta vez / nunca en este proyecto". "sí, siempre" → `FORGE local set surfaces.<name> allowed`; "nunca" → `denied`; "no, esta vez" writes nothing. Then run `verify-plan` again.
   - With `eligible: true`, decide per surface whether it is worth it and the depth (`smoke` or `flow`). A surface without `affects` (`match: null`) is verified only if the diff and its description are related. For each candidate you skip: `FORGE log --kind verify-skip --task <id>-<n> --data-file <f>` (`{"surface":"<name>","reason":"<one line>"}`). This also holds when you skip every surface of an eligible plan: log one `verify-skip` per surface, so the ledger records why nothing was verified.
   - If you verify: spawn `verify` (resolved with `FORGE agents`) **in parallel with the reviewers in step 4**, with the brief, the diff, the chosen surface files, the depth, the `missing` tools, review dir `.forge/work/<id>/reviews-<n>-<round>/` and evidence dir `.forge/work/<id>/evidence/<n>-<round>/` (`<round>` as step 4 defines it: 1 + the `round` value of the previous `FORGE round` call for this brief; 1 at first), the limits from `.forge/config.yaml`, the absolute FORGE path and, in a fix round, the previous `verify.json` of this brief. Never pass it a reviewer's output, nor its output to a reviewer.
4. `git diff $BASE..HEAD > .forge/work/<id>/diff-<n>.patch`. Spawn the `review-correctness` agent, and also `review-security` when `sensitive` is not empty (and `review-perf` for performance tasks), each with the brief, the diff, the validators file and the output dir `.forge/work/<id>/reviews-<n>-<round>/` (round = 1 + the `round` value of the previous `FORGE round` call for this brief; 1 at first). They run independently: spawn them in parallel and never pass one reviewer's output to another. Reviewers set `"approach": "wrong"` in their JSON when the change should be redone with another approach rather than patched.
5. Before calling the verdict, check that every spawned reviewer wrote its file (`correctness.json`, `security.json`, `perf.json`, and `verify.json` when `forge-verify` was spawned) in the review dir. `FORGE verdict` exits 2 when the dir holds none of them: if a reviewer did not write its file, resume it or respawn it; do not call the verdict without files.
6. `FORGE verdict --task <id>-<n> --dir .forge/work/<id>/reviews-<n>-<round> --validators .forge/work/<id>/validators-<n>.json` (add `--sensitive` when sensitive, `--perf` for performance tasks). If a reviewer in its output has `invalid: true`, respawn that reviewer once with the same inputs and the same dir and run the verdict again on that dir before trusting it (a verdict re-run on the same dir counts once). `invalid: true` with `dropped: 0` means its JSON was unusable and it abstained; with `dropped` > 0 only some findings were unusable: the review keeps its verdict and still scores. If it is still invalid after the respawn, keep the result as it is; when findings were dropped, read the reviewer's raw JSON file and record the dropped findings as a ruling (`FORGE log --kind ruling --task <id>-<n> --data-file <file>`, file: `{"dropped":[...]}`). Then `FORGE round --task <id>-<n> --path medium` and follow `next`. **Findings to send** below means the critical and important findings of the verdict plus the `failures` of every validator with `ok: false` in `validators-<n>.json`.
   - `done`: next task. Minor findings go to the ledger: `FORGE log --kind ruling --task <id>-<n> --data-file <file>` (file: `{"minor":[...]}`).
   - `resume`: send the findings to the same implementer (resume it), then repeat from step 3.
   - `fresh-stronger`: spawn a fresh implementer one tier up the ladder with the brief, the report and the findings to send, then repeat from step 3.
   - `redo`: undo the attempt without rewriting history: `git revert --no-edit $BASE..HEAD` (skip it when HEAD is still `BASE`), then a fresh implementer starts again from the brief with a different approach; repeat from step 3.
   - `breaker` or `stalled`: stop the loop. If what is open blocks the work, tell the user and ask; otherwise record the open findings as a ruling (`FORGE log --kind ruling --data-file <file>`) and continue, telling the user at the end.
   - `tierUp: true` (from round 3) and `fresh-stronger` mean the same single step up the ladder, not two: the implementer of that round is one tier above the one before it. With next = `redo` and `tierUp: true`, the fresh implementer is that one tier up.
   After the verdict, when `verify.json` exists:
   - Append its `learned` notes per surface: write a JSON array of the `note` strings for that surface to a file and run `FORGE surfaces learn --name <surface> --notes-file <f> --heading Aprendido` (or `Learned` in English); never add Learned notes with Edit, since `surfaces learn` keeps the surface's permission valid. If the returned `count` is over 20, propose to the user to summarise that section. The appended surface file is part of the task's changes: commit it with the task's work (or in the phase-close commit), so the tree is not left dirty.
   - Show its `proposals` to the user; apply a proposal to the surface file with Edit only after a yes, and then run `FORGE local set surfaces.<name> allowed` again.
   - Run `FORGE verify-cleanup --dir .forge/work/<id>/evidence/<n>-<round>/` (it stops anything the agent left running).
   - **Evidence on the roadmap.** When the task has a roadmap (`state/T`) and `.forge/config.yaml` has `evidence: upload` (the default): convert any screenshot over 2 MB to JPEG, upload the screenshots of this pass with the Artifact tool (`url: <roadmap url>`, `asset: true`, `file_paths: [...]`, up to 25 per call), then ArtifactData `update state/T` pinned to its version with `evidence: {surfaces, result, passed, total, local: "<evidence dir>", shots: [{url, id, surface, check, ok, expected, observed}]}`. Delete from the roadmap's assets the ids of the previous pass of this task. If the upload fails, write `evidence` without `url`/`id` and with `pending: true`, and retry on the next update of the task. With `evidence: local` or no roadmap, write `evidence` without `url`/`id`.
   A fail of `verify` is a finding like any other: its failed checks are in the verdict's critical/important lists and go in **Findings to send**.
7. Log the phase `done` (same file shape, with the last brief number), so the roadmap and lens show the run as finished. Then report: tasks, commits, verdict scores, rulings.

## Large

Subsystem, architecture, much ambiguity or risk, or a greenfield project. Gate: **mandatory approval** of the design.
1. **Design.** Log the phase `design` (and `plan` when step 2 starts, so lens shows where the run is). Run `/waypoint:design` to write and iterate `docs/waypoint/<project>/design.md` with the critic. Wait until the user approves it (`/waypoint:design approve`). Never approve it yourself. Under forge, `approve` runs only its steps 1–3 (approve, snapshot, publish); its step 4 (`waypoint:plan`) is replaced by step 2 below. That approval also covers the private roadmap publish that `/waypoint:plan` does. Once approved (the project id is known), write `.forge/work/<project>/run.json` with `{ "base": "<git rev-parse HEAD>" }` only if that file does not exist yet; never overwrite it (on resume it keeps the run's original base).
2. **Plan.** Get waypoint's CLI path with `FORGE waypoint-cli`. Spawn `forge-planner` with the design path, the plan path `docs/waypoint/<project>/plan.yaml`, the user's language, that path and the repo root. Show the user the phase outline it replies with and ask once for confirmation (as waypoint's plan step does). If the design's `start_prompt` contains `<track>`, rewrite it in `design.md` yourself: replace `<track>` with the id of the plan's first track and append ` — forge drives this session (forge:run Large loop)`, so the default becomes `/waypoint:work <track id> — forge drives this session (forge:run Large loop)` and parallel sessions launched from it run the forge loop too (`/waypoint:launch` adds the forge suffix to them when the design's `start_prompt` carries it) (small commit, no new design version). Then re-run `design-page` and re-publish to the design's `artifact` URL, as the `waypoint:plan` skill's `start_prompt` paragraph says. Then run `/waypoint:plan`: plan.yaml now exists, so it validates, publishes the live roadmap and syncs it.
3. **Tasks.** **Parallel or sequential.** The effective parallelism is `--parallel N` when the user gave it, else `swarm.parallel` from `.forge/config.yaml` (`FORGE agents` does not show it: read the file; default 5). A swarm member (its initial prompt says `swarm member of`, or `.waypoint/<project>/session.json` has `launchedBy`) skips this paragraph and goes on sequentially: members never coordinate. Otherwise, if it is 2 or more, this session becomes the swarm coordinator: follow **## Swarm** below instead of the rest of this step, and come back to step 4 when the swarm finishes. With 1, go on with this step.
   
   Run `/waypoint:work` and follow it, except that you replace only the first paragraph of its **§3 Do the work** ("Work the task with the normal workflow…") with this loop for the claimed task `T` (its id is the `<id>`; briefs are `T-<n>`). Everything else in §3 still applies: heartbeat (refresh it before each agent you spawn and at least every ~10 minutes; take the lease once before a step that spawns long agents — the implementer, or the batch of parallel reviewers: `update` `sessions/SID` `{heartbeatAt: NOW, busyUntil: <NOW + 90 min>}` pinned to `SV` (90 min is the cap), and delete it only when every agent spawned in that step has returned: `update` `{heartbeatAt: NOW, busyUntil: {"__delete__": true}}` pinned to `SV`, so other sessions do not recover the task meanwhile; if a step is still running after ~80 minutes (you get control back between agent returns), renew it with `{heartbeatAt: NOW, busyUntil: <NOW + 90 min>}`), intermediate commits, lost task, zone expansion, delegation, notes and the blocked path. If the loop ends in `breaker` or `stalled` with blocking findings, follow waypoint's blocked path (§3 blocked batch).
   - Before the loop, list `proposals` into the dbcache and run `FORGE proposals pull --dir <dbcache>/proposals`, so the local mirror is fresh.
   - **Forge state.** After each phase change and each verdict, ArtifactData `update` `state/T` `{forge: {path, phase, agent, validators: [{name, ok}], verdict: {action, score}, round, cap}}` pinned to `TV` (waypoint's task version). Keep it small: no findings text. On `version_mismatch` follow waypoint's lost-task rule. The same applies in Medium when a waypoint task is in progress.
   - `FORGE triage --plan <plan> --task T` (sensitive zones, files).
   - Run Medium steps 1–6 with `--path large` (cap 4) and **all three reviewers**: `review-correctness`, `review-security`, `review-perf` (pass `--sensitive` when triage found sensitive zones). Step 1: with no validators, the first task creates minimal tests. Step 2 starts at "record BASE": the brief comes from `mkdir -p .forge/work/T && FORGE brief --plan <plan> --task T > .forge/work/T/brief-1.md` (it carries the `Commit title prefix`), then append to that file anything the task needs that the plan does not say (design section, interfaces from earlier tasks). The implementer role is `impl-heavy` when the task touches a sensitive zone or the design marks it delicate, else `impl`.
   - Then continue `/waypoint:work` at §4. The implementers already committed, so at §4.1 skip the commit when the tree is clean; §4.2 `commit-info` of HEAD is what §4.4 records. Its commit rules and its phase-close merge authorization stay as they are.
4. **Final review.** When every task of the run is done (or at a phase close the user asks to review). Validation here includes the e2e and bench validators when the project has them: forge detects them; list them in `.forge/config.yaml` only when detection misses them.
   - `FORGE validate --final --task <project>-final > .forge/work/<project>/final-validators.json`.
   - `git diff <base>..HEAD > .forge/work/<project>/final.patch`, with `base` from `.forge/work/<project>/run.json`. After phase-close merges the diff includes the merged tracks; that is expected: the final review is of the whole run.
   - Spawn `review-correctness` in final review mode with the design path, the plan path and that diff, output dir `.forge/work/<project>/final-1/`. Then `FORGE verdict --task <project>-final --dir .forge/work/<project>/final-1 --validators .forge/work/<project>/final-validators.json` and act on the verdict's `action` (not the reviewer's own `verdict`).
   - If the action is `fix` or `redo` (a whole run is never redone: `redo` is treated as `fix`): one fix by `impl-heavy` with the final review JSON as its brief, report path `.forge/work/<project>/final-fix.txt`, task id `<project>-final`. Then the re-review, on fresh inputs: `FORGE validate --final --task <project>-final > .forge/work/<project>/final-validators-2.json`, `git diff <base>..HEAD > .forge/work/<project>/final-2.patch` (same `base` from `run.json`), spawn `review-correctness` in final review mode with the design path, the plan path and `final-2.patch`, output dir `.forge/work/<project>/final-2/`, then `FORGE verdict --task <project>-final --dir .forge/work/<project>/final-2 --validators .forge/work/<project>/final-validators-2.json`. Whatever remains goes to the user as rulings; no second fix.
   - The final review covers only what is merged into the current branch. With the verdict, list to the user the track branches not merged yet (`git branch --list 'track/*' --no-merged HEAD`): their work was not reviewed.
5. Log the phase `done`, then report: the roadmap URL, tasks done, verdict scores, rulings, unmerged track branches.

## Swarm

This session only coordinates: it never claims or works a task. It launches background sessions on tracks (fronts), each in its own worktree running this same forge loop, integrates their work into the base branch, and keeps the roadmap's `meta/swarm` up to date. `WP` = `FORGE waypoint-cli`; `DB` = `.waypoint/<project>/dbcache`; `SID` = this session's waypoint id from `.waypoint/<project>/session.json` (run `/waypoint:work` §0 Setup once if it does not exist, then stop following `/waypoint:work`).

This session's working directory is the main checkout for the whole swarm: never `cd` into a worktree (a command that must run elsewhere runs in a subshell, as the launch below does). `FORGE swarm start|tick|integrate|sleep|mark|retry` refuse to run outside the main checkout.

1. **Start (once).** Only from the main checkout (`MAIN_REPO`, as `/waypoint:work` §0.2 defines it). Make sure `plan.yaml` is committed. Ask the user once whether you may integrate the fronts' work into `<base branch>` (name the current branch; warn explicitly when it is `main` or the default branch) as it gets done (default: no; then finished fronts wait as "ready to integrate" and fronts that depend on them do not start). Run `FORGE swarm start --project <project> --session <SID> --parallel <N>` and add `--merge` if they said yes. It resumes a swarm this coordinator already had. Tell the user in a few lines: N slots, the base branch, whether you will integrate, that `/forge:stop` ends it, that no other session should be used in this main checkout while the swarm runs (the swarm binds to the first session the Stop hook sees), and that the background sessions ask for tool permissions in `claude agents` (shown as "Needs input"), where the user must approve them. Then end the turn once with no other text: the first Stop-hook block binds the swarm to this session and tells you to run the next tick; go on at step 2. In infinite mode (`/forge:infinite` step 3b, or a restart in a later cycle) do not end the turn here: the infinite run's own binding flow applies and you go on as `/forge:infinite` says.
2. **Read.** If `git status --porcelain docs/waypoint` shows changes to `plan.yaml` (e.g. tasks added from proposals), commit them (repository commit rules) so new worktrees see them. ArtifactData `update` `sessions/<SID>` `{heartbeatAt: NOW, status: "active"}` so the roadmap does not show the coordinator as idle. `node "<WP>" clean-cache <plan> state` and `... sessions`, then ArtifactData `list` both (`query: {limit: 1000}`, `out_dir: DB`). Call `ListAgents` and write to `.forge/work/swarm/agents.json`, as a JSON array of strings, only the names it shows as running or working, or as needing input; leave out the sessions it shows as idle, finished, done or exited (a name in that file keeps its front live).
3. **Decide.** `FORGE swarm tick --plan <plan> --db DB --agents .forge/work/swarm/agents.json` prints `{actions, progress, live, parallel}`.
4. **Act**, in the order the actions come:
   - `integrate {track, ref}`: `FORGE swarm integrate <track> --ref <ref>`, with the Bash tool's `timeout: 600000` (it runs the validators). Result `conflict`: write an escalation: ArtifactData `set` `messages/<EID>` (`EID` = `node "<WP>" event-id <SID>`) `{ts: NOW, from: SID, to: "*", type: "escalation", text: "<track>: <detail> — resolve it, then tell the swarm coordinator (<SID>), which runs forge swarm retry <track>", status: "open"}`, and tell the user. If the `detail` starts with "rollback failed", the main checkout itself needs manual attention: tell the user explicitly that the rollback failed and the main checkout must be fixed by hand, in addition to the escalation, and do not integrate anything else until they have fixed it. Result `main-dirty` with `first: true`: tell the user once that the main checkout must be clean and on the base branch for integration. While the main checkout is dirty or needs attention, keep ticking (launches still happen) but say nothing more to the user until it changes. After "rollback failed" tell the user once and skip every later `integrate` action until the user says it is fixed (launches continue). A `wait 0` after an `integrate` that did not return `integrated` is slept as step 6 says.
   - `launch {track}`: `node "<WP>" launch <plan> <track> --swarm <SID> --base <BASE>` (`BASE` = the `base` field of `FORGE swarm status`) → `{worktree, command}`; run it in a subshell, `(cd "<worktree>" && <command>)`, so this session's own working directory stays the main checkout. If it fails, write the error to `.forge/work/swarm/launch-<track>.txt`, run `FORGE swarm mark <track> --status launch-failed --detail-file <that file>` and tell the user (for "Workspace not trusted", give the same instructions `/waypoint:launch` step 6 gives).
   - `wait {seconds}`, `finish` or `stalled`: see steps 5-7.

   When the user says a conflict or a launch failure of a front is resolved (in chat, or by answering its escalation), run `FORGE swarm retry <track>` and resolve that escalation (pinned to its listed version); the next tick takes the front again. If the swarm had ended `stalled`, `retry` reactivates it with its fronts kept: tell the user in one line that the swarm is running again and go to step 2. If `FORGE swarm status` shows it still inactive (it was stopped, ran out of budget or finished), tell the user and that `/forge:run` starts a new swarm; do not tick. Otherwise, if your background `swarm sleep` is still running, end the turn without a tick; else go to step 2.
5. **Publish.** ArtifactData `update` `meta/swarm` with `file_path: .forge/swarm.json` (`set` it the first time, when `get` finds no document).
6. **Wait.** A `wait 0` means tick again at once ONLY when this tick's `integrate` returned `integrated`. Any other `wait 0` (integrate skipped, `main-dirty`, `conflict`, rollback failed) is treated as `wait 240`. With an effective wait above 0: first run `FORGE swarm sleep <seconds> --mark` in the foreground (it records the sleep and returns at once, so the Stop hook already knows), then run `FORGE swarm sleep <seconds>` with the Bash tool in the background (`run_in_background`), and end the turn without any other text. When it exits you are woken: first run `FORGE swarm status`; if the swarm is not active (stopped from elsewhere), go to step 7 (do not set the heartbeat `active`); otherwise go to step 2. With an effective wait of 0, go to step 2 at once. If the Stop hook blocks with `forge swarm is active` while your background `swarm sleep` is still running, just end the turn again without a tick. In infinite mode the sleep rule is this one, but the wake and end paths are the ones `/forge:infinite` §3.3 gives.
7. **End.** On `finish` or `stalled`, or when the Stop hook says `the forge swarm ended (<reason>)`: when you come here from step 6's wake check or from that Stop-hook message (not from a `finish` or `stalled` action of this tick, which step 5 has just published), first ArtifactData `get` `meta/swarm`; if it is already `active: false` with the same `stopReason` as `FORGE swarm status`, this end was already reported (e.g. by `/forge:stop`): say nothing more and stop. Otherwise publish once more (step 5), `update` `sessions/<SID>` `{status: "idle"}` and report to the user: fronts integrated, fronts left and why (the `stalled` reason), branches not integrated (`git branch --list 'track/*' --no-merged HEAD`), and the sessions still alive from `ListAgents`, which finish their current task and stop on their own. Then go to Large step 4 only when the swarm ended `finished` and everything is integrated; after `stopped`, `budget` or `stalled` just report and stop. After `stalled` on a conflict or launch failure, end the report by telling the user to say when it is resolved: the swarm then resumes from this session (the retry paragraph after step 4). In infinite mode, only the report applies (see `/forge:infinite` §3.3).

The Stop hook keeps this session going: when it blocks with `forge swarm is active`, go to step 2. It does not block while `swarm sleep` runs.

## Resuming

1. `FORGE last --task <id>`: `path` and `phase` (the whole last phase event, with its `brief` number `n`).
2. `FORGE last --task <id>-<n>`: the last verdict (with its review `dir`) and the last round of that brief.
3. Continue from there; the phase event's `base` is the `BASE` for `redo`; never redo finished work. If the last verdict already covers the newest review dir, do not run `FORGE verdict` on that dir again: go on with `FORGE round` (or the `next` of the last round). Run a verdict only for a review dir that has none yet.
