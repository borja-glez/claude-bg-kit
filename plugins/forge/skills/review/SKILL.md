# forge: review a branch

`FORGE` = `node "${CLAUDE_PLUGIN_ROOT}/dist/forge.cjs"`. Talk to the user in their language. This skill reviews and reports: it never fixes, merges or pushes.

1. **Base.** `<base>` = the argument, else `git merge-base HEAD <default branch>` (the default branch: `git symbolic-ref --short refs/remotes/origin/HEAD` without `origin/`, else `main`, else `master`). `<branch>` = `git branch --show-current` (detached: the short sha). When `git log --oneline <base>..HEAD` is empty, say there is nothing to review and stop. `<id>` = `review-<branch>-<tag>`: `<branch>` with every character outside `[A-Za-z0-9_.-]` turned into `-`, and `<tag>` made as `forge:run` makes the tag of loose ids (`### Ephemeral execution`, **Loose ids**). Work files go in `.forge/work/<id>/`.
2. **Tree.** `git status --porcelain`, as `forge:run`'s rules say: changes that are not forge's own → ask the user whether to commit, stash or leave them. "Leave them" means the baseline of step 3 is skipped, since switching commits would carry them: say so.
3. **Baseline.** With a clean tree: `git switch --detach <base>`, `FORGE validate --all --path medium --base-run --task <id> > .forge/work/<id>/baseline.json`, then switch back (`git switch <branch>`, or `git switch --detach <sha>` when HEAD was detached), always, also when the validators fail; check with `git rev-parse HEAD` that you are on the reviewed commit again before going on. Then `FORGE validate --all --path medium --base <base> --baseline .forge/work/<id>/baseline.json --task <id> > .forge/work/<id>/validators.json`. Without a baseline, the same command without `--baseline`: every failure counts.
4. **Diff and zones.** `git diff <base>..HEAD > .forge/work/<id>/diff-1.patch`. Write `.forge/work/<id>/task.txt` with the line «Review of <branch> against <base>» and the changed files (`git diff --name-only <base>..HEAD`), one per line, then `FORGE triage --task <id> --text-file .forge/work/<id>/task.txt`: its `sensitive` decides the security review.
5. **Brief.** Write `.forge/work/<id>/brief-1.md`: what the branch does (from `git log --format=%s%n%b <base>..HEAD`), the spec and plan it follows when the user or the commits name them (a superpowers spec or plan under `docs/superpowers/`), and «Review the whole branch; do not fix anything».
6. **Review.** Spawn `review-correctness`, plus `review-security` when `sensitive` is not empty and `review-perf` when the user asks about performance, in parallel (agents from `FORGE agents`), each with the brief, the diff, the validators file and the output dir `.forge/work/<id>/reviews-1-1/`. Wait for each file as `forge:run` Medium step 5 says. Then `FORGE verdict --task <id> --dir .forge/work/<id>/reviews-1-1 --validators .forge/work/<id>/validators.json` (`--sensitive` when sensitive, `--perf` with the perf review); a reviewer with `invalid: true` is respawned once, as in Medium step 6.
7. **Report.** The score, the verdict's `action` and the findings by severity (critical, important, minor), each with its file and line, plus the validators that fail and did not fail on the base. Then offer once to fix them with `/forge:run` on the Medium path, with these findings as its brief. Never merge, never push, never rewrite the branch's commits.
