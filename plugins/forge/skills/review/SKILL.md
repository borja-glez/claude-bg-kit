# forge: review a branch

`FORGE` = `node "${CLAUDE_PLUGIN_ROOT}/dist/forge.cjs"`. Talk to the user in their language. This skill reviews and reports: it never fixes, merges or pushes.

1. **Base.** `<base>` = the argument, else `git merge-base HEAD <default branch>` (the default branch: `git symbolic-ref --short refs/remotes/origin/HEAD` without `origin/`, else `main`, else `master`). `<branch>` = `git branch --show-current` (detached: the short sha). When `git log --oneline <base>..HEAD` is empty, say there is nothing to review and stop. `<id>` = `review-<branch>-<tag>`: `<branch>` with every character outside `[A-Za-z0-9_.-]` turned into `-` and cut to at most 40 characters, and `<tag>` made as `forge:run` makes the tag of loose ids (**Loose ids** in forge:run `references/ephemeral.md`). Work files go in `.forge/work/<id>/`.
2. **Tree.** `git status --porcelain`: changes that are not forge's own are not part of the review (it covers the commits `<base>..HEAD`), but the validators of step 3 run on this working tree and see them. Say so in one line and go on. This skill never commits, stashes or discards anything.
3. **Baseline**, in a temporary worktree, so this checkout never moves: `WT` = `.claude/worktrees/review-<tag>`, then `git worktree add --detach <WT> <base>`. Install its dependencies inside `<WT>` as forge does for a task worktree: `swarm.setup` of `.forge/config.yaml` when it is set, else by lockfile (`package-lock.json` → `npm ci`, `pnpm-lock.yaml` → `pnpm install --frozen-lockfile`, `yarn.lock` → `yarn install --frozen-lockfile`). Then `FORGE validate --all --path medium --base-run --task <id> --cwd <WT> > .forge/work/<id>/baseline.json`. When the worktree cannot be added, the project has no setup rule (a Python project without `swarm.setup`) or the setup fails, skip the baseline and say so: then every failure counts. Always remove the worktree afterwards, also when something failed: `git worktree remove --force <WT>` (it holds only this review's checkout of `<base>` and the dependencies installed in it). Then, in this checkout, `FORGE validate --all --path medium --base <base> --baseline .forge/work/<id>/baseline.json --task <id> > .forge/work/<id>/validators.json`, or the same command without `--baseline` when there is none.
4. **Diff and zones.** `git diff <base>..HEAD > .forge/work/<id>/diff-1.patch`. Write `.forge/work/<id>/task.txt` with the line «Review of <branch> against <base>» and the changed files (`git diff --name-only <base>..HEAD`), one per line (when the user asks about performance, also the line «Review its performance too.», so the triage adds `review-perf`), then `FORGE triage --task <id> --text-file .forge/work/<id>/task.txt`: its `sensitive` decides the security review and its `review` who reviews in step 6.
5. **Brief.** Write `.forge/work/<id>/brief-1.md`: what the branch does (from `git log --format=%s%n%b <base>..HEAD`), the spec and plan it follows when the user or the commits name them (a superpowers spec or plan under `docs/superpowers/`), and «Review the whole branch; do not fix anything».
6. **Review.** Spawn the reviewers of the step-4 triage's `review.reviewers` (`review-correctness`, plus `review-security` when `sensitive` is not empty; `review-perf` only when the user asked about performance, else leave it out), in parallel, each as its `agent`, passing the Agent tool's `effort` (the reviewer's `effort`) always and the Agent tool's `model` when the reviewer's is not null, each with the brief, the diff, the validators file and the output dir `.forge/work/<id>/reviews-1-1/`. Wait for each file as `forge:run` Medium step 5 says. Then `FORGE verdict --task <id> --dir .forge/work/<id>/reviews-1-1 --validators .forge/work/<id>/validators.json` (`--sensitive` when sensitive, `--perf` with the perf review); a reviewer with `invalid: true` is respawned once with the same effort and model, as in Medium step 6.
7. **Report.** The score, the verdict's `action` and the findings by severity (critical, important, minor), each with its file and line, plus the validators that fail: first those that did not fail on the base, then, marked «also failing on the base», those that did (the per-name baseline can hide a new failure in the same suite). Then offer once to fix them with `/forge:run` on the Medium path, with these findings as its brief. Never merge, never push, never rewrite the branch's commits.
