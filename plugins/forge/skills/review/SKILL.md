# forge: review a branch

`FORGE` = `node "${CLAUDE_PLUGIN_ROOT}/dist/forge.cjs"`. Talk to the user in their language. This skill reviews and reports: it never fixes, merges or pushes.

When a FORGE command exits 2 saying the commands of `.forge/config.yaml` are not trusted on this machine, write step 4's `task.txt`, run its `FORGE triage` and follow forge:run's `${CLAUDE_PLUGIN_ROOT}/skills/run/references/trust.md` with the `trust` it prints; then go on from where you were.

1. **Base.** `<base>` = the argument, else `git merge-base HEAD <default branch>` (the default branch: `git symbolic-ref --short refs/remotes/origin/HEAD` without `origin/`, else `main`, else `master`). `<branch>` = `git branch --show-current` (detached: the short sha). When `git log --oneline <base>..HEAD` is empty, say there is nothing to review and stop. `<id>` = `review-<branch>-<tag>`: `<branch>` with every character outside `[A-Za-z0-9_.-]` turned into `-` and cut to at most 40 characters, and `<tag>` made as `forge:run` makes the tag of loose ids (**Loose ids** in forge:run `references/ephemeral.md`). Work files go in `.forge/work/<id>/`.
2. **Tree.** `git status --porcelain`: changes that are not forge's own are not part of the review (it covers the commits `<base>..HEAD`), but the validators of step 3 run on this working tree and see them. Say so in one line and go on. This skill never commits, stashes or discards anything.
3. **Baseline**, in a temporary worktree, so this checkout never moves: `WT` = `.claude/worktrees/review-<tag>`, then `git worktree add --detach <WT> <base>`. Install its dependencies with `FORGE setup --cwd <WT>`: forge's own rule for a task worktree (`swarm.setup` of `.forge/config.yaml`, else the install command of the lockfile); it prints `{setup}`, `null` when there is nothing to install. Then `FORGE validate --all --path medium --base-run --task <id> --cwd <WT> > .forge/work/<id>/baseline.json`. When the worktree cannot be added or `setup.ok` is false (it failed, or a Python project has no `swarm.setup`), skip the baseline and say so: then every failure counts. Always remove the worktree afterwards, also when something failed: `git worktree remove --force <WT>` (it holds only this review's checkout of `<base>` and the dependencies installed in it). When there is no baseline, write `[]` to `.forge/work/<id>/baseline.json` with the Write tool (then every failure counts). `FORGE review-prep` (step 6) validates this checkout against it.
4. **Zones.** Write `.forge/work/<id>/task.txt` with the line «Review of <branch> against <base>» and the changed files (`git diff --name-only <base>..HEAD`), one per line (when the user asks about performance, also the line «Review its performance too.», so the triage adds `review-perf`), then `FORGE triage --task <id> --text-file .forge/work/<id>/task.txt --base <base>`, so the real diff `<base>..HEAD` sizes the review: its `review` says who reviews, and `FORGE review-prep` reads it in step 6.
5. **Brief.** Write `.forge/work/<id>/brief-1.md`: what the branch does (from `git log --format=%s%n%b <base>..HEAD`), the spec and plan it follows when the user or the commits name them (a superpowers spec or plan under `docs/superpowers/`), and «Review the whole branch; do not fix anything».
6. **Review.** `FORGE review-prep --task <id>-1 --path medium --base <base> --baseline .forge/work/<id>/baseline.json --dir .forge/work/<id> --report --locale <es|en>` (add `--sensitive` when the user asks for a security review: security then reviews whatever the diff touches; without it, only when the diff touches a sensitive zone). It validates this checkout against the baseline into `.forge/work/<id>/validators-1.json`, writes the diff, reads the step-4 triage's `review` and prints `spawn`; print its `say`. Then `FORGE verify-plan --task <id>-1 --path medium --base <base> --locale <es|en>`: when it prints `eligible: true`, a surface that asks or `drafts`, offer once to verify the branch with them, as forge:run `references/verify.md` `## Before the review` says; on yes, `FORGE verify-env --task <id>-1 --dir .forge/work/<id>/reviews-1-1` and spawn `verify` next to the reviewers, with this checkout (the one under review, never `<WT>`, already removed) as its code checkout. Spawn each entry of review-prep's `spawn` in parallel, each as subagent type `forge:<agent>` (its `agent`) with its `inputs`, passing the Agent tool's `effort` always and its `model` when the entry's is not null, and start each prompt with the line `forge-task: <id>-1`. Wait for each file as `forge:run` Medium step 5 says. Then `FORGE review-close --task <id>-1 --dir .forge/work/<id> --path medium --locale <es|en>`: exit 3 with `missing` respawns, once, each reviewer it lists with its same entry (a `verify.json`: the verify agent); a reviewer in `invalid` or `incomplete` (a draft with `complete: false`) is respawned once with the same entry and dir (it picks up its own draft) and the round closed again. Its `next` is not followed: this skill fixes nothing. When `verify.json` exists, close it as forge:run `references/verify.md` `## After the verdict` says, except the evidence on the roadmap; commit nothing: the files in its `commit` stay as changes of this tree, and the report says so.
7. **Report.** Log the phase `done`: write `{"phase":"done","brief":1,"base":"<base>"}` to `.forge/work/<id>/done.json` with the Write tool and run `FORGE log --kind phase --task <id> --data-file .forge/work/<id>/done.json`, so lens no longer shows the review open. Then the score, review-close's `action` and the findings by severity: the critical and important ones of its `findings` file (when it wrote one), the ones that do not block from its `deferred` (each with its `residual`) and its `minor`, each with its file and line, plus the validators that fail (`.forge/work/<id>/validators-1.json`): first those that did not fail on the base, then, marked «also failing on the base», those that did (the per-name baseline can hide a new failure in the same suite). When verify ran, also name the surface files verify-close changed (its `commit`), left uncommitted for the person to keep or discard, and the defects it turned into proposals (`defects.added`, pending in `.forge/proposals/`). Then offer once to fix them with `/forge:run` on the Medium path, with these findings as its brief. Never merge, never push, never rewrite the branch's commits.
